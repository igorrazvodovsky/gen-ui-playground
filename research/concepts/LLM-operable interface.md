A system designed not just to be *generated by* an LLM but to be *operated by* one at runtime. This means every configurable surface — catalog entries, mapping rules, data model schemas, layout parameters — is exposed in a format the LLM can inspect, reason about, and modify through clean tool-callable interfaces. The distinction is between a system where the LLM writes the spec once and walks away, versus one where the LLM continuously navigates the configuration space as a mediator between user and system.

## Context

Most LLM-in-the-loop systems treat the LLM as a one-shot generator: prompt in, artifact out. The LAUI vision requires something different — the LLM as a persistent operator that configures and reconfigures the system in response to evolving user needs. Flute X GPT illustrates this: the agent has a set of functions it can call (SetHapticMode, ToggleVisual, ModifyTempo, SelectSegment, etc.) and it invokes them dynamically based on its assessment of the student's progress. The system is designed to be *driven* by the agent.

This maps onto the generative UI pipeline: instead of the LLM generating a complete UI spec once, it should be able to modify individual aspects — swap a component, adjust a layout rule, restructure a data relationship — through targeted operations.

## Connections

- Constrains [[component catalog as schema]] — the catalog isn't just a rendering lookup table; it's an agent's menu of options. Catalog entries need semantic metadata (when to use this component, what data shapes it handles, what interaction it affords) so the agent can make informed selections.
- Constrains [[specification-based rendering]] — specs must be granularly modifiable, not monolithic. If the only operation is "replace entire spec," the agent can't make surgical adjustments.
- Enables [[emergent workflow]] — the agent can only discover emergent workflows if the system's surfaces are navigable. Opaque or monolithic interfaces force one-shot generation; operable interfaces enable continuous adaptation.
- Relates to [[guardrailed generative UI]] — guardrails (schema validation, component whitelisting) serve double duty: they constrain the LLM's generation *and* they define the safe operating envelope for runtime modifications.
- **User profile as operand:** [[context-driven adaptation]] — the user profile model is another surface the agent can inspect and act on. "This user has low vision" → agent selects high-contrast variants, increases target sizes. The profile schema needs to be agent-readable (semantic keys, not opaque blobs), just like the catalog and spec schemas.

## Relevance to project

This is the most immediately actionable of the three LAUI concepts. It's a design constraint that should inform current build decisions:

1. **Catalog design**: Include semantic metadata per component — not just `{type, props}` but also usage hints, data shape expectations, and interaction descriptions. This costs nothing now and saves a retrofit later.
2. **Spec granularity**: Ensure specs are composed of independently addressable sub-specs (per-component, per-section) rather than one flat JSON blob. This enables targeted modifications.
3. **Pipeline stage interfaces**: Each stage (task analysis → data model → UI spec → rendered UI) should have a defined input/output contract that an agent could call as a tool. Even if no agent exists yet, designing the stages as callable functions rather than one monolithic pipeline keeps the option open.

## Open threads

- What metadata does an agent actually need per catalog entry? The LAUI paper doesn't specify — it just says the agent is "initialised to be proficient with the system." In practice, this is a prompt engineering / tool description design problem.
- How do you balance granular operability with coherence? If the agent can modify any individual component, what ensures the overall UI stays coherent? Guardrails help, but they only catch schema violations, not aesthetic or UX incoherence.
- Performance: if the agent makes many small modifications, how does the rendering pipeline handle incremental updates? Full re-render from spec is expensive for large UIs.
