A structured representation of the entities, attributes, relationships, and constraints that describe the problem domain. Not what the user wants to *do* (that's the [[task-model]]), but what the data *is* — its shape, types, cardinalities, and semantic relationships. The domain data model is the substrate that UI components bind to and that [[constraint-driven component selection]] rules read from.

## Context

Every UI ultimately renders data. The domain data model defines that data's structure: a recipe has a title (string), ingredients (array of objects with name, quantity, unit), prep time (duration), and serves (integer). It also defines relationships: a recipe belongs to a collection, references ingredients from a pantry, and may link to meal plans. And it defines constraints: title is required, serves is at least 1, ingredients must have at least one entry.

This sits at a specific point on the [[structured vs unstructured tension]] spectrum. A full OWL ontology ([[ontology-driven UI generation]]) is the richest possible domain data model — class hierarchies, semantic relationships, formal cardinalities, foundational ontology reuse. A JSON Schema is lighter — types, required fields, enums, array bounds. [[generative-malleable-UI|JELLY]]'s "task-driven data model" is somewhere between: object-relational schemas with entity-relationship semantics, generated by the LLM from user intent.

The richer the domain data model, the more the pipeline can do deterministically. With bare types (string, number, boolean), you get basic [[constraint-driven component selection]]. With cardinalities (`only`, `some`, `min 1`), you get structural constraints (dropdowns, required fields, bounded lists). With semantic relationships (class hierarchies, domain-specific annotations), you get intelligent defaults and pattern selection. The trade-off: richer models are harder for the LLM to generate reliably.

## Connections

- **Distinct from** [[task-model]] — the task model captures what users do; the domain data model captures what the data looks like. They change independently: same data, different tasks (browsing vs. editing recipes); same task pattern (search → filter → select), different data
- **Input to** [[constraint-driven component selection]] — cardinalities and types mechanically determine which components render each field. The domain data model is what the constraint rules read
- **Input to** [[fluid-attributes]] — Meridian's attribute configuration layer sits directly above the domain data model. Native attributes map 1:1 from data fields; derived attributes compute across fields; AI-reformulated attributes transform fields via LLM prompts. The domain data model defines what's available; the attribute config defines how it's presented
- **Enriched by** [[ontology-driven UI generation]] — formal ontologies are the richest form of domain data model, encoding semantic relationships and class hierarchies beyond what JSON Schema captures
- **Layer in** [[model hierarchy]] — traditionally treated as an input to the task model rather than a layer in the hierarchy itself. But JELLY makes it primary, and the pipeline sketch puts it as an explicit artefact between task analysis and attribute configuration
- **Bound to UI via** [[specification-based rendering]] — json-render specs bind component props to data values. A2UI's `BoundValue` pattern separates the component tree from the data model entirely, with JSON pointer paths as the binding mechanism. The domain data model is what those pointers point at
- **Enables** [[ai-attribute-reformulation]] — reformulation prompts operate on domain data model fields. "Summarise reviews as sentiment" requires knowing that `reviews` is an array of text. The model's type information constrains what reformulations are valid
- **Relates to** [[concept-as-composition-unit]] — Varv's concepts bundle state schemas (domain data model fragments) with behaviour (actions) and triggers. The domain data model is the state portion of a concept. Déjà Vu's concepts each own their own data model, composed via [[identity-based-data-integration]]
- **Relates to** [[abstract-concrete-separation]] — the domain data model is abstract (platform-independent data shape). Its binding to UI components is concrete (platform-specific rendering). Varv's abstract concept definitions are essentially domain data models with behaviour attached
- **Evolved via** [[accretive-extensibility]] — Meridian shows that user customisations to the data model (adding derived attributes, reformulation prompts) can be spec overlays on the base model, not edits to it. This makes regeneration safe — the base model can change without destroying user modifications
- **Shared across tools via** [[shared data layer]] — if multiple tools operate on the same domain data model (a map tool shows locations, a list tool shows details, a calendar shows dates), the data model is the integration point

## Practical implementations

- **JSON Schema** — the most common lightweight domain data model. Types, required fields, enums, array constraints, `$ref` for relationships. Used by react-jsonschema-form, OpenAPI, and most schema-to-UI tools.
- **Prisma schema** — a domain data model DSL for databases. Models, fields, relations, constraints. Prisma Studio generates admin UIs from it.
- **GraphQL schema** — types, fields, relationships, nullability. Drives both API shape and frontend data requirements.
- **Zod / Yup / Joi** — runtime schema validation libraries that double as domain data models in TypeScript/JavaScript applications.
- **Django / Rails models** — ORM model definitions that describe entities, fields, relationships, and constraints. Drive both database schema and admin UI generation.
- **Airtable field definitions** — each field has a type (single select, linked record, formula, etc.) that determines both storage and rendering. Essentially a visual domain data model editor.
- **OWL ontologies** — the heavyweight option. Full semantic relationships, class hierarchies, formal cardinalities, foundational ontology reuse (BFO). Used by Protege, TopBraid, and the Nunes et al. system.

## Relevance to project

The domain data model is the pipeline's central artefact — almost everything downstream reads from it. [[constraint-driven component selection]] reads types and cardinalities. [[fluid-attributes]] reads field definitions. [[pattern-driven transformation]] reads entity structure to determine which patterns apply. [[ai-attribute-reformulation]] reads field types to constrain what transformations are valid.

For the pipeline, the LLM generates the domain data model from the [[task-model]]: "the dinner party planner needs these tasks" → "those tasks require these entities (guests, dishes, timeline events) with these attributes and relationships." The key question is how much constraint metadata to include. Bare types (string, number) enable basic component selection. Adding cardinalities (required, optional, one-of-many) enables structural constraints. Adding semantic annotations (this string is an email, this number is a currency amount) enables intelligent formatting and validation.

The pragmatic target: JSON Schema enriched with semantic annotations — richer than bare types, lighter than OWL. Something like:

```json
{
  "guest": {
    "name": { "type": "string", "required": true },
    "email": { "type": "string", "format": "email" },
    "dietary": { "type": "string", "enum": ["none", "vegetarian", "vegan", "gluten-free"] },
    "rsvp": { "type": "boolean", "default": false }
  }
}
```

This gives [[constraint-driven component selection]] enough to work with (enum → dropdown, boolean → toggle, required → mandatory field) while staying within what an LLM can reliably generate.

## Open threads

- How much semantic enrichment can the LLM reliably add? Bare types are easy; cardinalities are tractable; semantic relationships (this entity is a specialisation of that entity) are harder. Where's the reliability cliff?
- Should the domain data model include *behaviour* (valid state transitions, business rules), or just structure? Varv says yes — [[software-as-data-structure]]. The pragmatic answer depends on whether the LLM can generate correct state machines.
- How does the domain data model evolve when user requirements change? Full regeneration loses user customisations. [[accretive-extensibility]] (overlay modifications) preserves them but can produce inconsistencies. Cambria's bidirectional lenses are a third option for schema migration.
- Can domain data models be partially reused across tasks? A "contacts" model (name, email, phone, address) recurs across event planning, CRM, mailing lists. A [[concept-catalog]] at the data model level could provide reusable schema fragments.
- A2UI's separation of data model from component tree (binding via JSON pointer paths) suggests the domain data model should be a *standalone artefact*, not embedded in the component spec. This enables reactive two-way binding: the component tree stays stable when data changes; only the bound values update.
