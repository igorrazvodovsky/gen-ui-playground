The intermediate states of UI generation — not just the final output — are themselves the primary customisation interface. Instead of generating a complete UI and then offering modification tools, the system renders each generation stage as a visible, interactive partial UI. Users discover what's customisable by rewinding to the layer where that dimension was decided. A video homepage that generates through Categories → Layout → Content → Style gives users four distinct customisation surfaces, each operating in a different vocabulary and at a different abstraction level.

## Context

Min et al. (2026) observe that current genUI designs face a dilemma: prompt boxes lack affordances for customisation discovery, but traditional menu-based approaches can't scale to the vast customisation space that generative systems enable. Their insight is that the generation process already passes through meaningful intermediate states — the system just doesn't show them. Making these states visible and navigable turns the generation timeline into a customisation navigation axis.

The key design decision is *what* the layers are. The paper argues designers should identify them by reflecting on their own design process — what intermediate artefacts do they produce when going from brief to final UI? For a scheduling calendar: first decide *whose* data to show (Data layer), then *what metadata* to surface (Information layer), then *how* to represent time (Time Slots layer), then *how it looks* (Style layer). Each layer has its own specification format because each operates at a different abstraction level — natural language for content selection, JSON schemas for structural layout, typed interfaces for data shaping, CSS variables for visual styling.

This is architecturally distinct from both the pre-generation transparency checkpoints (intent decomposition, semantic specification) and the post-generation verification layers (requirements/assumptions decomposition). Those are pipeline-internal representations made visible. Generation layers are *rendered partial UIs* — the user sees actual interface elements at each stage, not abstract representations of the system's decisions.

## Connections

- **Extends** [[gentle slope]] — adds a new navigation axis. The existing slope runs vertically through abstraction levels (view → tweak values → edit specs → edit models). Generation layers add a *horizontal* axis: rewind through the generation timeline to access different customisation dimensions. A user who wants to change the layout doesn't need to understand specs — they rewind to the layout layer and drag sections around.
- **Concretises** [[configuration-model-as-design-space]] — Kumbang's configuration space is abstract (variation points + constraints). Generation layers are one way to *navigate* that space: each layer exposes a slice of the configuration dimensions, and rewinding to a layer is equivalent to selecting a dimension to adjust. The layer stack defines a traversal order through the configuration space.
- **Contrasts with** [[staged-co-generation]] — DuetUI's stages are *temporal phases of collaboration* (Define → Empathise → Plan → Explore → Refine → Duet), where the user and agent negotiate intent over time. Generation layers are *structural dimensions of the output*, where each layer corresponds to a class of design decisions. Staged co-generation is about how the conversation unfolds; layered generation is about how the artefact assembles. They're complementary: the staged collaboration could happen *within* each generation layer.
- **Operationalises** [[dimensions-of-meaningful-variation]] — Zhang et al.'s theory says a notation must choose which dimensions of variation to foreground. Each generation layer foregrounds one dimension (categories, layout, content, style) and makes it directly manipulable. The layer stack is a prioritised ordering of the task's meaningful dimensions. Designers choose which dimensions get their own layer — a consequential decision, because un-layered dimensions become harder to discover.
- **Relates to** [[semantic-intermediate-layer]] — Park et al.'s semantic layer is a *single* inspectable representation between intent and output. Generation layers are *multiple* partial UIs between intent and output. The semantic layer shows design decisions as structured data (slots, hierarchies); generation layers show them as rendered interface states. The semantic layer is more powerful for expert users who can read the decomposition; generation layers are more accessible because the user sees actual UI.
- **Tension with** [[accretive-extensibility]] — Varv's overlay model allows modification by addition to the final spec. Generation layers allow modification by rewinding to an earlier stage. These are different modification metaphors (spatial layering vs. temporal rewinding) that could coexist: user customisations at each generation layer could be stored as spec overlays.
- **Informs** [[model hierarchy]] — the MBUI model hierarchy (Task → Dialog → Presentation → Layout) is a pipeline-internal abstraction stack. Generation layers are its user-facing projection — each generation layer corresponds roughly to a model hierarchy level, but rendered as an intermediate UI rather than an abstract model. The paper's four-layer examples don't map 1:1 to the model hierarchy (the Data/Information/TimeSlots/Style split for calendars is task-specific, not generic), suggesting that generation layers should be task-driven, not architecturally fixed.
- **Informed by** [[fluid-attributes]] — the Content layer in the video homepage prototype (which attributes appear per video, how they're filtered) is structurally the same as Meridian's attribute configuration. This suggests [[fluid-attributes]] is the natural customisation mechanism for content-level generation layers.

## Practical implementations

- **Min et al.'s prototypes** (2026) — video feed homepage, team scheduling calendar, course management system. Demonstrations only, no deployed systems.
- **Figma's auto-layout** — when auto-layout generates a frame, intermediate states (content → spacing → alignment → responsive rules) are implicitly layered. Users can "rewind" by selecting a nested frame and modifying its auto-layout properties without affecting outer layers.
- **CSS cascade** — the cascade itself is a layered generation process: user-agent styles → author reset → base styles → component styles → theme overrides → utility classes. DevTools lets users inspect and modify at each layer. This is generation-layer-as-customisation-surface for styling, already widely deployed.
- **Webflow's designer** — generation progresses through structure (HTML) → layout (flexbox/grid) → styling (visual) → interactions (animations). Each is a distinct panel. Users navigate customisation by selecting the right panel, not by understanding the full cascade.

## Relevance to project

This concept sits between the pipeline's pre-generation transparency layers and the post-generation customisation loop. The architecture sketch currently shows generation as a single step (UI specification → Rendered UI). This paper argues that step should be decomposed into visible sub-steps, each producing a partial UI the user can inspect and modify before generation proceeds.

For the pipeline, the question becomes: which of the existing pipeline stages (task analysis → data model → attribute config → view config → UI spec → adaptation) should produce user-visible intermediate UIs? Not all of them — that's too many checkpoints. The paper suggests the answer is task-specific: a scheduling app benefits from Data → TimeSlots → Style layers, while a content feed benefits from Categories → Layout → Content → Style. The layer selection is itself a design decision that belongs in the pattern library or task analysis stage.

The specification-format-per-layer finding is directly relevant to the intermediate representation question (open design question 1). It suggests the answer isn't a single format but a stack: natural language specs for high-abstraction layers, JSON schemas for structural layers, typed interfaces for data layers, CSS variables for style layers. The pipeline already has this implicitly (intent is NL, specs are JSON, adaptation rules are structured) — this paper argues for making the multiplicity explicit and user-facing.

## Open threads

- **Layer selection automation**: can the LLM identify appropriate generation layers for a given task, or must designers pre-define them? The paper assumes designer-defined layers, but for truly generative systems the layers themselves might need to be generated.
- **Layer granularity trade-off**: too few layers and customisation discovery suffers; too many and the generation process becomes tedious. What's the right number? The paper uses 4 consistently — is this a design heuristic or coincidence?
- **Personal layers at scale**: the paper proposes end-users can add their own layers. How does the system validate that a user-defined layer is compatible with the existing stack? What happens when personal layers conflict with designer-defined ones?
- **Rewinding cost**: changing an early layer (e.g. Categories) cascades through all subsequent layers. How does the system communicate this cost? Can it preserve user customisations in later layers when an earlier layer changes, or must they be regenerated?
