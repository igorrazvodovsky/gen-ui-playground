Using an inferred objective to generate a complete, functional interactive tool — not just text or a static UI, but a working software application with interactive features, data displays, and integrated AI capabilities. The objective steers tool *design* (what the tool does, how it's structured) and tool *evaluation* (whether the implementation serves the user's goal). Each generated tool is unique to the user's context and task.

## Context

Most generative UI research produces either static layouts (JELLY, Meridian) or pre-defined component configurations (json-render). Poppins-tools goes further: it generates entire bespoke applications — a Character Emotion Tracker for a fiction writer, a Neural Architecture Search Explorer for a microcontroller researcher, a Scientific Palette Generator for a figure designer. The generation pipeline is: objective → tool design specification (function, implementation approach, interface features, design guidelines) → code generation (Svelte component) → critique/refinement → rendered tool.

## Connections

- Enabled by [[generate-then-rank-with-objectives]] — the objective steers both the design specification and the code evaluation
- Extends [[two-step generative UI]] (AG-UI) — AG-UI separates "what UI" from "how to build it"; Poppins-tools adds "why this UI" (the objective) as an upstream steering signal
- Tension with [[specification-based rendering]] — json-render generates validated specs that map to a known component catalog; Poppins generates freeform code with no catalog constraints. The json-render approach is more predictable; the Poppins approach is more flexible. The pipeline likely needs both: catalog-constrained generation for structured data views, freeform generation for novel tool types
- Relates to [[component catalog as schema]] — Poppins uses an LLM helper library (getExperts, promptGeneral) as a lightweight capability catalog, but doesn't constrain *UI components* to a catalog. The helper library is a functional catalog (what operations are available), not a presentational one (what widgets exist)
- Tension with [[guardrailed generative UI]] — generated Svelte code can contain bugs, non-functional buttons, flawed LLM response parsing. The paper acknowledges this. json-render's schema validation + component whitelisting avoids this class of errors entirely but sacrifices flexibility

## Practical implementations

- Poppins-tools (Lam et al., 2026) — generates Svelte components with access to an LLM helper function library
- The tool design specification format (high-level function description + implementation approach + interface features + design guidelines + problem settings) is a reusable intermediate representation for any tool generation pipeline

## Relevance to project

This is the closest existing system to the full generative UI vision — it actually generates working, task-specific interactive tools from inferred user objectives. But it diverges from the pipeline in important ways:

1. **No persistent data model.** Each Poppins tool is generated fresh. There's no task-driven data model that persists and evolves. The pipeline's DataConfig → AttributeConfig → ViewConfig → LayoutConfig hierarchy doesn't exist here.
2. **No component catalog constraints.** Poppins generates arbitrary Svelte code. The pipeline constrains generation to catalog components for predictability.
3. **No accretive modification.** Users can regenerate or tweak objectives, but there's no overlay model for incremental customisation ([[accretive-extensibility]]). Each generation is a fresh start.
4. **One-shot, not continuous.** The tool is generated, used, and discarded. There's no feedback loop into model evolution.

The tool design specification format is worth studying as a potential intermediate representation for the pipeline's spec generation stage — it captures function, approach, and interface features in a way that's richer than a flat UI spec but less structured than Meridian's four-layer config.

The study finding that 11/17 participants preferred Poppins-experts (text feedback) over Poppins-tools (generated UIs) is a useful calibration: full tool generation may not be what users want most of the time. The pipeline should support a spectrum from lightweight text responses through structured feedback to full interactive tools, with the objective determining which mode to use.

## Open threads

- Can objective-driven generation work *within* a catalog-constrained system? I.e., use the objective to select and configure catalog components rather than generating freeform code? This would combine JIT's personalisation with json-render's predictability.
- The tool design specification is generated by one LLM call, then code is generated by another. How many intermediate specification steps are optimal before committing to code? The pipeline suggests more (task analysis → data model → attribute config → view config → UI spec); Poppins suggests fewer (objective → tool spec → code). The right answer likely depends on the complexity of the target UI.
- Generated tools sometimes include non-functional elements (buttons that don't work, flawed parsing). How does this affect user trust? DuetUI found that a single data error caused "collapse of trust." If generated tools are buggy, the trust cost may outweigh the personalisation benefit.
