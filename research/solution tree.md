# Opportunity solution tree

> [!info] Framework
> Structured as an [opportunity solution tree](https://www.producttalk.org/opportunity-solution-trees/) (Teresa Torres). The outcome at the root sets scope. Opportunities are the problem space — user needs, pain points, and gaps that must be addressed for the outcome to be real. Solutions are specific approaches to each opportunity. Experiments test the riskiest assumptions in each solution.

## Outcome

**Users describe a task in natural language → get a working, modifiable UI → the system evolves as their needs change.**

This is the JELLY vision ([[generative-malleable-UI|JELLY]]). The pipeline from [[project|project.md]] is the architectural hypothesis for how to get there:

```
Persistent intent spec + Per-session prompt + User context + Domain model (via MCP)
  → [PRE-GEN: process transparency — user steers]
    Intent decomposition → Semantic parse → Task analysis → Data model → Attribute config → UI spec → Adaptation
  → [GENERATION] Rendered UI + per-item attribute reformulation
  → [POST-GEN: outcome transparency — user verifies]
    Requirements/Assumptions decomposition → Augmented semantics → Traceability
  ↺ Scoped refinement + Intent spec update candidates → Model evolution
```

(See [[synthesis#Architecture sketch]] for the full version with protocol stack and checkpoint density notes.)

The opportunities below map to gaps in this pipeline — places where we don't yet know if or how the thing works.

## Opportunity 1 — Generated UIs are disposable

Users can't meaningfully modify a generated interface. Every generation is a one-shot: take it or re-prompt. This makes the system a fancy screenshot generator, not a malleable tool.

This is the biggest experiential gap. If users can't *work with* the generated output — tweaking values, restructuring views, adding fields — the whole pipeline is a parlour trick.

### O1a — Changes don't propagate

When a user edits the UI (changes a value, toggles a switch, rearranges a list), nothing updates upstream. The underlying spec doesn't know the UI changed. Next regeneration wipes everything.

**Solutions:**

- **S1: Two-way reactive binding (DFRP)** — [[json-document-backed-components]] from Malleable Software. React components read from *and write to* a shared JSON document. json-render currently only reads; making it write-back is the minimum viable step. AG-UI's [[shared data layer]] provides a concrete protocol: StateSnapshot for full state, StateDelta with JSON Patch (RFC 6902) for incremental updates. This makes the agent-frontend binding bidirectional over a network boundary, not just co-located.
  - *Experiment:* Build the simplest round-trip — a component rendered from a JSON spec where editing a value in the UI updates the spec, and spec changes re-render the component. %%Validates: reactive binding works with json-render's architecture%%
  - *Experiment:* Test update granularity — full spec replacement vs. surgical JSON patches (RFC 6902). Measure re-render performance and state preservation.

- **S2: Accretive overlays (Varv pattern)** — [[accretive-extensibility]]. User modifications are stored as a separate overlay layer, not edits to the base spec. Regeneration replaces the base; user overlays survive. Reversible by removing the overlay.
  - *Experiment:* Implement a two-layer spec: base (generated) + overlay (user edits). Regenerate the base and verify overlays still apply correctly. Test edge cases: what happens when a regeneration removes an element the overlay modifies?

- **S3: Abstract/concrete separation** — [[abstract-concrete-separation]] from Varv. Separate the *semantic* layer (what entities exist, what actions are valid) from the *binding* layer (which components render them, which layout). User edits to the concrete layer don't affect the abstract layer and vice versa.
  - *Experiment:* Express a simple task (e.g. a reading list) as abstract model + concrete bindings. Change the bindings (swap table for cards) and verify the abstract model is untouched. Change the abstract model (add a field) and verify bindings extend gracefully.

- **S3b: Configuration space with constraint checking** — [[configuration-model-as-design-space]], [[feature-component-duality]] from Kumbang. Instead of a single spec, generate a constrained configuration space: the spec includes variation points (optional components, alternative views, configurable attributes) and cross-cutting constraints (if calendar view is removed, deadline field still needs *some* display). User customisation becomes navigation within this space, with automatic consistency checking after each change. Prevents users from creating invalid UI states.
  - *Experiment:* Take the reading list task. Define variation points: view mode (table | cards | list), optional fields (rating, notes, cover image), sort options. Define constraints: at least one view must be active, the primary field (title) can't be removed. Implement a simple constraint checker. Test: can a user navigate the space fluidly? Does constraint checking feel helpful or restrictive?

- **S4: In-place inspection toolchain** — [[in-place toolchain]]. Embed editing tools within the running interface (cf. JELLY's inspect tool). Click a component → see its spec, data source, and mapping rule. Edit in place. This is the [[gentle slope]] mechanism: the user doesn't need to know the spec format, they explore it through the UI they're already using. Modifications propagate via S1 (two-way binding) or S2 (overlay).
  - *Experiment:* Build an inspect overlay for a json-render output. Can a user identify *why* a field is rendered as a dropdown vs. a text input? Can they change the mapping? Does the change propagate to the spec and survive regeneration (via S2)?

### O1b — Users can't steer generation before it happens

The system goes from prompt to rendered UI in one opaque leap. Users have no way to see or adjust the system's interpretation — its task decomposition, pattern selections, or semantic slots — before committing to a generation pass. Every disagreement surfaces after the fact, turning steering into repair.

**Solutions:**

- **S5: Semantic intermediate layer (visible)** — [[semantic-intermediate-layer]], [[hierarchical-design-semantics]]. Before rendering, show the user a structured decomposition of what the system understood: Product → Design System → Feature → Component (Park et al.). The user reviews and edits this before compilation. Makes the generation legible.
  - *Experiment:* For a generated UI, produce the semantic decomposition as a visible, editable artefact. Measure: does exposing this layer improve users' ability to steer the output? (Park et al. say yes — p<.001 for perceived control.)

- **S5b: Process surrogate (pattern selection rationale)** — [[surrogate-process]], [[three-alignment-gulfs]]. The pipeline's most opaque step is the LLM choosing patterns and components. A surrogate process shows the user a simplified, controllable representation of *why* the system made its choices (e.g., "I chose Search pattern because your task involves filtering entities; Table for results because you have 5+ comparable items with shared attributes"). This bridges the Process Gulf identified by Terry et al. — users need to understand and potentially control *how* the AI generates, not just *what* it generates.
  - *Experiment:* Generate a UI for one of the example tasks. Before rendering, present a pattern selection rationale (which patterns were considered, which were chosen and why). Measure: does the rationale help users redirect *wrong* choices before generation? Can they correct a pattern selection and trigger targeted regeneration?

- **S5e: JIT objective induction as pre-prompt entry point** — [[just-in-time-objective-induction]], [[generate-then-rank-with-objectives]]. Before the user even types a prompt, observe their current context (workspace, open documents, interaction history) and induce candidate objectives. Present these as a starting point for the intent decomposition cascade (S10). Lam et al. (CHI '26) demonstrate 75–80% accuracy with a single screenshot; a system with richer context (existing data model, interaction history) could do better. The [[generate-then-rank-with-objectives]] pattern — applying the objective to both generation and evaluation via simple prompt prepend — achieves 66–86% win rates over unsteered baselines with trivial implementation cost. Addresses the blank-page problem: users who don't know what to ask for get a starting point. Caution: 97.8% selection rate for system-generated objectives suggests anchoring bias — objectives must be clearly presented as suggestions, not facts.
  - *Experiment:* For three example tasks, provide context screenshots (a half-finished spreadsheet, a research paper draft, a travel planning doc). Run objective induction. Measure: (a) how many of the induced objectives are accurate and useful (per user self-report)? (b) Do users who start from induced objectives produce better final UIs than users who start from blank prompts? (c) How often do users accept induced objectives unchanged vs. modify them?

- **S5d: Generation layers as steering surfaces** — [[generation-layer-as-customisation-surface]]. Instead of a single pre-generation checkpoint (semantic review), decompose generation into multiple visible intermediate UI layers (e.g. Categories → Layout → Content → Style). Each layer renders as a partial UI the user can inspect and modify before generation proceeds to the next layer. The generation timeline becomes a navigation axis for customisation discovery — users rewind to access different customisation dimensions. Different from S5 (which shows abstract semantic decomposition): generation layers show *actual partial UIs*, making them accessible to users who can't read structured specifications. Min et al. (2026, same lab as JELLY) demonstrate this for three app types. Layer selection is task-specific (a scheduling app uses Data → TimeSlots → Style; a content feed uses Categories → Layout → Content → Style).
  - *Experiment:* Take one of the example tasks (e.g. apartment comparison). Define 3–4 generation layers, each with layer-appropriate customisation controls. Generate the UI layer by layer. Measure: (a) do users discover more customisation options than with one-shot generation? (b) Is the overhead of reviewing intermediate layers acceptable? (c) Does rewinding to an earlier layer (and cascading changes through subsequent layers) feel predictable or disorienting?

### O1c — Iteration is divergent, not convergent

Re-prompting drifts. Each conversational turn can shift the entire output unpredictably ([[semantic-drift]]). There's no mechanism for targeted, structural edits that preserve what's already working. DuetUI's user study (N=24) provides direct evidence: participants overwhelmingly preferred iterative refinement over one-shot generation, and [[tangible-agency]] controls (sliders, pickers, buttons) enabled targeted modifications without re-prompting. The [[bidirectional-context-loop]] makes iteration convergent by default — user manipulations feed back as scoped context, not unconstrained re-prompts.

**Solutions:**

- **S6: Scoped semantic editing** — [[scoped-semantic-editing]]. Edits target specific semantic anchors (a field, a component, a layout region) via diffs rather than re-prompting the whole thing. Prevents drift, makes iteration convergent.
  - *Experiment:* Generate a multi-component interface. Ask the user to modify one section. Compare scoped editing (change just that section's spec) vs. re-prompting (describe the change in natural language). Measure drift in the unchanged sections.

- **S6b: Paradigm-informed interaction design** — [[paradigm-graph-as-design-language]], [[prompt-interaction-synergy]]. Instead of ad-hoc interaction patterns for the customisation loop, systematically select from IAI's 12 atomic paradigms based on the design situation. Use Table 3's cheat sheet: pre-invocation artifact-grounded (P3, P4) for initial specification with examples; post-invocation prompt-only (P5, P6) for exploratory refinement; post-invocation artifact-grounded (P8, P12) for persistent widget-driven iteration. Different pipeline stages may warrant different paradigm types. The [[augmented-instruction]] entity should be an explicit, inspectable artefact in the pipeline — not implicit string concatenation.
  - *Experiment:* For one example task, implement three customisation interaction modes corresponding to three paradigm types: (a) P1-style interactive prompt enhancement (text editing only), (b) P7-style generative prompt control widgets (AI-generated sliders/controls), (c) P4-style artifact-grounded instruction (selecting components + text command). Compare user satisfaction, iteration speed, and output quality. Measure: does the paradigm type affect convergence rate?

### O1d — Users can't verify generated output without over-trusting it

After generation, users need to evaluate whether the output is correct. But the obvious approach — showing them the process that produced it (step-by-step rationale, task graph, pattern selection trace) — backfires. [[process-induced-overreliance]] (Grunde-McLaughlin et al., 2026): a reasonable-looking process narrative short-circuits critical evaluation. Users who saw detailed process traces achieved *worse* error detection (39.13%) than those who saw outcome decompositions (77.14%). The false confidence finding (Hedges' g: 0.85) compounds this — users with better tools were *more confident when wrong*.

This is structurally different from O1b (pre-gen steering). O1b asks "can the user redirect before generation?" O1d asks "can the user catch errors after generation?" The temporal transparency principle says these need different designs: process-oriented for O1b, outcome-oriented for O1d.

**Solutions:**

- **S5c: Outcome-oriented verification (Requirements/Assumptions)** — [[outcome-oriented-verification]]. After generation, decompose the output into Requirements (what the user explicitly asked for, mapped to specific components) and Assumptions (what the LLM inferred, added, or decided unilaterally). Forces per-assumption evaluation rather than holistic impression formation. Grunde-McLaughlin et al. showed 77.14% error-finding accuracy vs. 39.13% for process-oriented traces.
  - *Experiment:* Generate a UI for an example task. Present the output with a Requirements/Assumptions panel. Measure: can users identify incorrect assumptions? Can they reject an assumption and trigger regeneration of just the assumption-driven components? Compare with baseline (no decomposition) and with S5b's process rationale shown post-gen (expect S5b to *underperform* baseline due to overreliance). Key metric: false confidence — are users who miss errors more or less confident than baseline?

- **S19b: Augmented semantics for assumption surfacing** — [[augmented-semantics]], [[intent-output-traceability]]. Automated companion to S5c. After generation, extract what the AI actually implemented (augmented semantics) and compare against the stated intent. Classify each generated element as requirement-driven or assumption-driven. Feed the classification to S5c's Requirements/Assumptions panel. This makes S5c's decomposition evidence-based rather than LLM-asserted. (See also S19 under O4c for the automated verification angle — S19 catches *structural* semantic errors; S19b surfaces *inferential* assumptions for human review.)
  - *Experiment:* Generate specs for example tasks. Run the augmented semantics extraction. Measure: how accurately can the system classify elements as requirement-driven vs. assumption-driven? What's the agreement rate with human judges? Does automated classification improve the quality of the Requirements/Assumptions panel (compared to LLM self-report)?

## Opportunity 2 — The gap between user task and component spec is too wide

json-render needs `{type, props, children}`. Users think in terms of "plan a dinner party" or "compare apartments." The distance between these is enormous. Jumping it in one step — LLM takes prompt, outputs component spec — is fragile, unvalidatable, and opaque.

### O2a — No intermediate representation

There's nowhere for the system to represent *what the user is working with* in a form that's richer than a prompt but simpler than a component tree. This is the [[structured vs unstructured tension]] at the pipeline's core.

**Solutions:**

- **S7: Task-driven data model (JELLY-style)** — [[domain-data-model]], [[task-model]]. An IR built around the user's task: entities, attributes, relationships, constraints. "Dinner party" → guests (list of people), menu (list of dishes, each with dietary tags), timeline (sequence of events). The IR captures the *what* without committing to the *how* (which components). The modelling process should use **competency questions (CQs)** as the requirements capture step before schema authoring — CQs ground each entity and relationship in a concrete question the UI needs to answer (eXtreme Design methodology; validated by Lippolis et al. 2025 for LLM-driven ontology generation).
  - *Experiment:* For 3–5 example tasks (dinner party, apartment comparison, reading list, project tracker, CPQ product configuration): (1) Write 10–15 competency questions per task — questions the generated UI must be able to answer (e.g. "Which guests have dietary constraints?", "What dishes satisfy a given constraint?", "What's the preparation timeline?"). (2) Hand-author IRs to answer those CQs. (3) Compile each to valid json-render specs. Evaluate: do the generated UIs make sense? Is the IR expressive enough? Do the CQs catch missing entities/relationships that would otherwise surface only at UI generation time?
  - *Experiment:* Compare hand-authored IRs with **LLM-generated IRs from CQs**. Feed the same CQs + user story to an LLM using the Memoryless CQbyCQ pattern (Lippolis et al. 2025): generate a schema fragment per CQ independently, then merge. This tests whether CQ-driven LLM generation produces usable task-driven data models without hand-authoring. Measure: schema completeness (does the merged IR answer all CQs?), superfluous elements (does it generate entities/properties no CQ needs?), and downstream UI quality (do the generated UIs from hand-authored vs. LLM-generated IRs differ meaningfully?). The memoryless approach is preferred over incremental accumulation — Lippolis et al. found that accumulated context *distracts* the LLM, causing it to optimise for consistency with previous (possibly wrong) decisions rather than modelling each requirement cleanly.

- **S8: Concept-based composition (Déjà Vu / Varv)** — [[concept-as-composition-unit]], [[concept-catalog]]. Instead of a flat schema, the IR is a set of composable concepts, each with schema + actions + bindings. "Dinner party" composes Guest, Dish, DietaryConstraint, Timeline concepts.
  - *Revised position:* Concept composition should **not** be the default IR approach. Per [[concept-as-behavioural-annotation]], most UIs compose structurally (patterns + components) without needing named behavioural specs. Concepts become the IR only when **state transitions and side effects create behavioural complexity** that S7's flat model can't express (auth flows, scoring, approval workflows). Start with S7; add concept specs selectively when S7 hits the wall. The concept catalog remains valuable as a **knowledge resource** (concept-named prompts improve LLM generation quality — [[concept-spec-as-generation-checkpoint]]) and as the vocabulary for the behavioural rule layer when needed.
  - *Experiment (revised):* Take 3–5 example tasks. Start with S7 (task-driven data model). Identify which tasks, if any, have behavioural complexity that S7 handles poorly. For those, express the problematic behaviour as concept specs. Compare: does the concept-augmented version generate better UIs for the complex cases? Does it add overhead for the simple ones?

- **S9: Multi-level IR chain** — [[hierarchical-design-semantics]], [[model hierarchy]]. Not one IR but a chain: intent IR (what the user wants) → data IR (what entities exist) → presentation IR (what components to use). Each level is independently validatable and editable.
  - *Experiment:* Build the chain for one example task. Test: can a user edit at the data IR level (add a field) and have the change propagate cleanly to the presentation IR and then to json-render? How much of the chain can be automated vs. requires human choice?

### O2b — Data relationships and constraints aren't captured

Flat attribute lists don't encode that a dish *belongs to* a menu, that a guest *has* dietary requirements that *constrain* available dishes, or that a pricing tier *depends on* channel eligibility. Without relationships, the generated UI can't show connected views (e.g. [[overview-detail-pattern]]) or enforce business logic.

**Solutions:**

- **S10: Object-relational schema (JELLY's SVAL/DICT/PNTR/ARRY)** — The IR includes typed relationships: PNTR (reference to another entity), ARRY (ordered collection), DICT (key-value). This is the minimal relational layer.
  - *Experiment:* Take the apartment comparison task. Model it with PNTR (apartment → neighbourhood, apartment → landlord) and ARRY (apartment → photos). Verify the json-render output can express the relationships (e.g. clicking an apartment shows its neighbourhood detail).

- **S11: Knowledge graph layer** — [[knowledge-graph-grounded-generation]]. For domain-specific tasks, the IR references a knowledge graph encoding domain constraints, valid configurations, and business rules. For stable, well-understood domains (as opposed to ad-hoc task domains in S7), this layer can be built using CQ-driven LLM ontology generation (Lippolis et al. 2025) — the LLM generates OWL-level ontological structure from competency questions, then the knowledge graph serves as persistent grounding for all subsequent generation.
  - *Experiment:* Build a minimal CPQ knowledge graph (products, channels, pricing rules, eligibility constraints). Generate task models from natural language intent. Measure: does the knowledge graph catch invalid configurations the LLM would otherwise hallucinate? (Fareedi et al. show 15% accuracy improvement with grounding.)
  - *Experiment:* Test CQ-driven knowledge graph bootstrapping for the CPQ domain. Write domain CQs ("Can Product A be sold in Channel B?", "What pricing tiers apply to a given product-channel combination?"). Generate ontological structure using Memoryless CQbyCQ or Ontogenia (Lippolis et al. 2025). Evaluate: is the generated structure usable as a knowledge graph for grounding, or does it need significant manual correction? Compare bootstrapping cost (CQs + LLM generation + human review) vs. fully manual authoring.

## Opportunity 3 — The system lacks structured design knowledge

The pipeline needs to make design decisions at multiple levels — and currently has no principled basis for any of them. Component selection (date → date picker vs. calendar vs. text input) is the obvious case, but it's one facet of a broader problem: the system also needs to select **modalities** (contextual widget vs. full-screen canvas — [[modality-as-task-container]]), manage **cognitive load** (how many elements to show given user state and display constraints — [[cognitive-load-bounded-display]], [[optimisation-based-ui-adaptation]]), and **adapt to user context** (accessibility needs, preferences, environment — [[context-driven adaptation]]). Without encoded design knowledge at each of these levels, the system either makes arbitrary choices, always picks the default, or delegates everything to the LLM's training-data priors.

**Solutions:**

- **S12: Pattern library (static rules)** — [[pattern-driven transformation]], [[design systems as pattern libraries]], [[pattern composition]]. A hand-authored rule set: data type × cardinality × task context → component choice. "List of items with 2–5 attributes each, comparison task → table. Same list, browsing task → cards." This covers the component-selection level. It doesn't cover modality selection or cognitive load — those need separate rule layers.
  - *Experiment:* Author mapping rules for the 3–5 example tasks from O2a experiments. Evaluate the generated UIs. Are the component choices defensible? Where do the rules break down (what contexts aren't captured)?

- **S13: Constraint-driven selection** — [[constraint-driven component selection]], [[sufficiency-criteria]], [[configuration-model-as-design-space]]. Instead of direct rules, define constraints: "this component needs at least 3 items to be useful," "this layout requires a primary/secondary data split." The mapping becomes a constraint satisfaction problem. Kumbang's constraint language (predicates like `present(ref)`, `instanceOf(ref, T)`, `connectedTo(ref1, ref2)`, `cardinality(ref)`) provides a vocabulary richer than simple type→component mappings — it can express cross-cutting dependencies between features and components ([[feature-component-duality]]). Stefanidi et al. (2022) take this further with [[optimisation-based-ui-adaptation]]: constraints + scoring → combinatorial optimisation that jointly handles selection, level of detail, and placement. This generalises from "which component for this field" to "which subset of components for this display, given limited screen/cognitive space." The [[cognitive-load-bounded-display]] constraint (max visible elements varies with user state) is a concrete constraint type. Constraint-driven selection naturally absorbs modality and cognitive load as additional constraint dimensions — it's the most architecturally general approach.
  - *Experiment:* Express the pattern library rules as constraints. Feed them to a solver (or to the LLM as prompt context). Does constraint framing handle edge cases better than direct rules? Is it more composable? Additionally: add one cognitive load constraint (max N visible elements for this user state) and one modality constraint (task complexity → minimum modality size). Do these integrate naturally with component-level constraints?

- **S14: LLM-selected with pattern guidance** — Give the LLM the component catalog + the pattern library as context, and let it choose. The pattern library isn't deterministic rules — it's a set of examples and heuristics the LLM reasons over.
  - *Experiment:* Compare three conditions: (a) LLM with no design guidance, (b) LLM with pattern library as prompt context, (c) deterministic pattern rules. Evaluate on the example tasks. Measure: appropriateness of component choices, handling of ambiguous cases, consistency across runs.

## Opportunity 4 — Natural language can't reliably become structured task models

This is the generative core. Everything else is plumbing. If the LLM can't take "help me plan a dinner party" and produce a useful, structured representation of that task, the pipeline fails regardless of how good the rendering is.

### O4a — Users express intent ambiguously

"Plan a dinner party" doesn't specify: how many guests, dietary constraints, budget, whether they want a timeline or just a menu, whether "plan" means "generate a checklist" or "build an interactive tool." The LLM must either guess or ask, and guessing is fragile.

**Solutions:**

- **S15: Intent decomposition (IntentFlow)** — [[intent-decomposition]], [[intent-decomposition]]. Decompose the prompt into Goal → Intents → Intent Dimensions before generating anything. "Plan dinner party" → Goal: plan event → Intents: manage guests, design menu, schedule timeline → Dimensions: guest count (slider), dietary options (multi-select), formality level (toggle). Users refine the dimensions before generation.
  - *Experiment:* Implement intent decomposition for the example tasks. Measure: does the decomposition surface requirements the user didn't explicitly state ([[reflection-in-intent]])? Does editing intent dimensions change the generated output in predictable ways?

- **S16: Progressive disclosure** — Auto-generate a reasonable default, but expose intent dimensions on demand. Simple tasks get one-shot generation; complex tasks get the decomposition layer when the user wants it. Terry et al.'s [[alignment-cost-tradeoff]] strengthens this: alignment has costs, and for low-stakes tasks, acting first and refining retrospectively is cheaper than full prospective specification. The pipeline should support both a "quick generate" path (skip checkpoints) and a "guided generate" path (full intent decomposition + semantic review). Raees et al.'s [[cognitive-engagement-for-reliance]] reframes this further: progressive disclosure isn't just about reducing friction — it's about building reliance scaffolding. Each checkpoint the user engages with builds their capacity to appropriately delegate at the next stage. The "guided generate" path should be structured as exploration → experimentation → construction → evaluation, not just "review this, then review that."
  - *Experiment:* Test with users at varying task complexity. At what complexity threshold does progressive disclosure (showing the intent layer) improve output quality vs. just regenerating? Additionally, measure reliance calibration: does structured analytical engagement (what-if on intent dimensions) produce better reliance than passive review?

- **S16b: Intent tags (user-driven micro-prompting)** — [[intent-tag-as-micro-prompt]], [[graduated-ambiguity-tolerance]]. Instead of system-driven decomposition (S15), let users build intent incrementally via atomic [label: value] tags on a spatial canvas. Supports [[graduated-ambiguity-tolerance]]: users specify precisely where they care, vaguely where they don't. System supplements with [[meta-intent-elicitation]] — suggesting tags the user hasn't considered. Hybrid entry: initial prompt → auto-grounded tags → user refinement.
  - *Experiment:* Compare three intent specification modes for the example tasks: (a) free-text prompt only, (b) IntentFlow-style system decomposition (S15), (c) intent tag canvas with suggestions. Measure: output alignment with user intent, perceived control, time to satisfactory result. Does the hybrid (grounding from prompt → tags → edit) outperform either pure approach?

### O4d — Intent doesn't persist across sessions

O4a–O4b address per-session ambiguity: the user types something, the system resolves it *this time*. But preferences, conventions, and domain constraints recur across sessions. Every new session starts from zero — the system has no memory of past resolutions. Users re-specify the same things ("I always want tables for lists," "our brand uses sentence case") or silently accept defaults that diverge from their preferences.

This is architecturally different from per-session resolution. The mechanism isn't decomposition or elicitation — it's **accumulation and maintenance** of a persistent, human-readable coordination document.

**Solutions:**

- **S16c: Persistent intent specification (cross-session accumulation)** — [[intent-specification-as-common-ground]], [[impact-analysis-before-generation]]. Accumulate resolved preferences in a persistent document (CLAUDE.md / cursor rules equivalent). Each session starts with the accumulated context. When the user makes choices that refine or contradict existing preferences, surface the change as a candidate "commit" with impact analysis (show what other generated UIs would change). SemanticCommit validates: KG-based conflict detection, 1.6× recall improvement, users prefer impact-first workflow (6/12 always checked conflicts first).
  - *Experiment:* Implement a minimal intent specification file. Generate UIs across 3–5 sessions for related tasks. After each session, surface candidate preference commits (e.g., "you consistently chose table views — add 'prefer tables for lists' to your spec?"). Measure: does cross-session accumulation improve generation alignment over time? Does the impact analysis help users make confident commit decisions? Compare with baseline (no persistent spec — each session starts fresh).

- **S16d: Usage-derived preference extraction** — [[usage-as-annotation]], [[cross-task-user-knowledge]]. Instead of (or alongside) explicit preference commits, infer preferences from interaction patterns. The user resizes columns, reorders fields, switches from cards to table — these are implicit preference signals. Aggregate into candidate knowledge items with content + scope + confidence (InterQuest model). Use [[uncertainty-driven-elicitation]] to confirm high-impact, low-confidence items ("I noticed you always expand the notes column — should I make text fields wider by default?"). Complements S16c: S16c handles explicit preference management, S16d handles implicit preference discovery.
  - *Experiment:* Instrument a generated UI to capture interaction events (resizes, reorderings, view switches, field additions/removals). After 3–5 tasks, aggregate into candidate preference items. Measure: do the inferred preferences match user self-report? Does applying them to the next generation improve satisfaction? How many interaction events are needed before signals become reliable?

### O4b — Implicit requirements aren't surfaced

"Make Product A available in Channel B" implies: check eligibility rules, configure product attributes for the channel, set pricing, possibly create an approval workflow. The LLM needs domain knowledge to surface these implicit sub-tasks — not just language understanding.

**Solutions:**

- **S17: Knowledge-grounded generation** — [[knowledge-graph-grounded-generation]]. The LLM queries a structured knowledge store (product schemas, business rules, vocabulary mappings) to decompose intent into operations. The knowledge store is the domain expertise the LLM lacks. The CQ-driven approach (Lippolis et al. 2025) suggests a concrete mechanism: express domain knowledge as competency questions, use the LLM to generate ontological structure from them, then use that structure as grounding context for task decomposition. This separates the *knowledge capture* step (CQs → ontology) from the *generation* step (intent + ontology → task model).
  - *Experiment:* Hand-author 5–10 tasks at varying ambiguity. Provide domain knowledge as LLM context. Evaluate: do task decompositions capture implicit requirements? Does a domain expert recognise them as correct and complete?
  - *Experiment:* Vary the knowledge representation (minimal JSON schemas → schemas + rules + glossary → queryable knowledge graph). Measure decomposition quality at each level. Find the minimum viable knowledge store.
  - *Experiment:* Test CQ-driven knowledge capture as the input mechanism for grounding. For one domain (e.g. CPQ): (a) write domain CQs with a domain expert, (b) generate ontological structure from CQs using an LLM, (c) use the generated structure as grounding context for task decomposition. Compare against hand-authored domain schemas as grounding. Key question: does the CQ-driven approach surface implicit domain requirements that hand-authored schemas miss (because CQs force you to articulate what you need to *ask*, not just what you need to *store*)?

- **S18: Grounding by example** — [[grounding-by-example]]. Instead of (or alongside) a knowledge graph, provide the LLM with examples of correct task decompositions for the domain. Few-shot learning for domain expertise.
  - *Experiment:* Compare knowledge graph grounding (S17) vs. example-based grounding vs. both combined. Measure accuracy on held-out tasks.

### O4c — Generated output can't be validated for semantic correctness

Schema validation catches structural errors (missing required field, wrong type). It can't catch semantic errors: mapping a person's name to a number input, using a date picker for a freetext description, generating a pricing form that violates business rules.

**Solutions:**

- **S19: Augmented semantics (verification loop)** — [[augmented-semantics]], [[intent-output-traceability]]. After generation, run an *automated* verification pass: does the output trace back to the stated intent? Do component choices match the semantic type of each field? Flag mismatches for human review. This catches *structural* semantic errors (name mapped to number input, date to freetext). Complements S5c/S19b under O1d, which handle *inferential* errors (wrong assumptions) via human review. S19 is the automated gate; O1d is the human verification layer. Both are post-generation, outcome-oriented. If CQs were used in S7 to define the task model, they provide a natural verification criterion: can the generated UI answer each CQ? A CQ that has no corresponding UI element indicates a coverage gap; a UI element that maps to no CQ indicates a superfluous element (Lippolis et al. 2025 found superfluous elements are LLMs' most persistent modelling weakness).
  - *Experiment:* Generate specs for the example tasks. Deliberately introduce semantic errors. Can the verification pass detect them? What's the false positive rate?
  - *Experiment:* CQ-based coverage verification. For tasks that have CQs (from S7), generate UI specs and attempt to map each CQ to one or more UI elements. Measure: CQ coverage (proportion of CQs answerable by the generated UI), superfluous element rate (proportion of UI elements that don't map to any CQ), and false negatives (CQs that *are* answerable but the automated check misses). This adapts Lippolis et al.'s "proportion of modelled CQs" metric from ontology evaluation to UI evaluation.

- **S20: Adaptation quality gates** — [[adaptation-quality-gates]], [[sufficiency-criteria]]. Define minimum quality criteria for generated output: coverage (all intent dimensions addressed), coherence (no contradictory component choices), sufficiency (each component has enough data to be useful). CQ coverage (from S19) provides a concrete sufficiency criterion: the UI passes if it can answer all CQs defined for the task.
  - *Experiment:* Apply quality gates to LLM-generated specs. Measure: how often does generation pass on first attempt? What are the common failure modes? Does iterative regeneration (LLM fixes its own failures) converge?

## Opportunity 5 — The end-to-end loop doesn't cohere

Each segment might work in isolation but fail at the seams. The original seam list focused on the generation pipeline: intent → IR, IR → spec, spec → user edit, user edit → IR. But the late-stage papers surfaced additional integration boundaries:

- **Persistent intent spec ↔ per-session generation** — How does the accumulated intent specification compose with this session's prompt? When they conflict, what wins? (SemanticCommit)
- **Protocol stack ↔ pipeline engine** — The pipeline engine sits between MCP (data/tools below) and AG-UI (user above). Does the protocol abstraction leak? Do AG-UI's event semantics match the pipeline's state transitions? (AG-UI, MCP)
- **Pre-gen → post-gen temporal mode switch** — The pipeline has two transparency modes with different design principles. How does the system signal the transition? During iterative refinement, does each cycle reset to pre-gen or stay in post-gen? (Grunde-McLaughlin)
- **User knowledge base ↔ adaptation layer** — The dual-structure user model (taxonomy for accessibility, fluid scope for preferences) feeds the adaptation layer. But the two sub-models have different update mechanisms (deterministic rules vs. entropy-driven elicitation). How does the adaptation layer reconcile them? (InterQuest, OADAPT)

**Solutions:**

- **S21: Vertical slice integration** — Pick one example task. Wire the full pipeline: prompt → intent decomposition → IR → mapping → json-render → user edit → IR update → re-render. Test every seam. The runtime layer needs an [[event-driven agent-UI protocol]] — the persistent bidirectional connection (event streams, state sync, frontend-defined tools) that makes the feedback loop work as a continuous process rather than discrete request-response cycles.
  - *Experiment:* A user describes a task, gets a generated UI, modifies it (changes a value, adds a field, restructures a view), and the system updates coherently. Not polished — just not broken. Specifically test: does a user edit propagate to the IR, the task model, or both? Full regeneration vs. incremental spec patching (JSON Patch deltas vs. full snapshots)? What happens when a user edit conflicts with the generated structure?

- **S22: Domain-specific end-to-end (via WebMCP)** — [[task-model]] validated against the existing application. User states intent in business language → system decomposes → executes against real app via WebMCP → result matches what a human operator would have done.
  - *Experiment:* Expose key operations as WebMCP tools. Map task model operations to tool calls. Test the feedback loop: execution failure → re-plan → retry. Evaluate: is the result recognisably correct?

- **S23: Bidirectional context loop prototype (DuetUI-inspired)** — [[bidirectional-context-loop]], [[tangible-agency]], [[task-interface-duality]]. Build a minimal co-generation prototype: the agent decomposes a task into subtasks, generates a UI with embedded agent-interactive controls, captures user actions as context, and updates the UI based on inferred intent. Tests the collaboration paradigm independently of the full pipeline. DuetUI validates this pattern (SUS 73.65 vs. 63.5, p=.002) but with simulated data. Testing with real APIs would validate feasibility.
  - *Experiment:* Take one example task (e.g., travel planning). Implement the bidirectional loop: agent generates task-structured UI with [[tangible-agency]] controls → user manipulates controls → agent reads action history + current spec → updates task decomposition and UI. Measure: does the loop converge on a useful result? How many cycles? What's the latency per cycle? Compare with a prompt-only baseline.

- **S24: New-seam integration test** — Specifically test the integration boundaries that S21–S23 don't cover. These are the seams introduced by the late-stage papers, not the original pipeline seams.
  - *Experiment (intent spec composition):* Create a persistent intent spec with 3–5 preferences. Issue a per-session prompt that conflicts with one preference. Does the system detect the conflict? Does it generate according to the prompt (override) or the spec (persist)? Is the conflict surfaced to the user?
  - *Experiment (temporal mode transition):* Wire pre-gen steering (S5) and post-gen verification (S5c) into the same pipeline. Generate, verify, then request a scoped edit (S6). Does the system switch back to pre-gen mode for the edit? Or stay in post-gen mode? What feels right to the user?
  - *Experiment (protocol stack integration):* Serve the pipeline's spec via AG-UI events (StateSnapshot → StateDelta stream). Does the AG-UI event model naturally represent the pipeline's state transitions (intent parsed → semantic slots filled → spec generated → rendered)? Where does the abstraction break down?

## Cross-cutting concerns

These aren't opportunities in the tree sense — they're constraints and questions that cut across multiple branches.

- **[[streaming specification compilation]]** — Latency. If generation takes 10 seconds, the UX is dead. Streaming (render as the spec arrives) is a baseline requirement, not an experiment.
- **[[guardrailed generative UI]]** — Safety. The component catalog is the contract boundary. Everything upstream must produce specs that conform. The three-layer guardrail pattern (schema validation → semantic check → runtime constraint) applies across the pipeline. AG-UI adds a fourth dimension: [[frontend-defined tool execution]] constrains what *actions* the agent can take at runtime, not just what *output* it can produce. Tool availability is runtime-configurable — dynamic guardrails via dynamic tool sets.
- **Runtime protocol** — The [[event-driven agent-UI protocol]] (AG-UI) provides the persistent, bidirectional connection the feedback loop requires. Event streaming, [[shared data layer]] via JSON Patch, and frontend-defined tools are shared infrastructure that serves both the generative UI pipeline and the broader [[vision tree|LLM-operable interface vision]].
- **WebMCP tool granularity** — For experiments: should WebMCP tools be high-level ("configure product for channel") or low-level ("fill field X, click button Y")? High-level is reliable but rigid; low-level is brittle but composable.
- **Domain knowledge maintenance** — If the domain changes (new products, new rules), who updates the knowledge store? Can the system detect drift? CQ-driven ontology generation (Lippolis et al. 2025) suggests a maintenance mechanism: when domain changes occur, express them as new or modified CQs, regenerate affected schema fragments using the Memoryless CQbyCQ pattern, and merge into the existing knowledge store. The CQ set itself becomes a human-readable specification of what the knowledge store must support — similar to how the intent specification (S16c) accumulates user preferences.
- **CQ-driven modelling as shared process** — Competency questions (from eXtreme Design, validated for LLM generation by Lippolis et al. 2025) are a cross-cutting methodological concern, not just an S7 technique. CQs serve three roles across the pipeline: (1) **requirements capture** — grounding domain models in concrete questions the UI must answer (S7, S11), (2) **evaluation criteria** — automated coverage checks post-generation (S19, S20), and (3) **knowledge elicitation** — structuring conversations with domain experts to capture implicit requirements (S17). The CQ set for a task is a reusable artefact that persists across experiments. For ad-hoc task domains (dinner party, apartment comparison), CQs are lightweight and disposable. For stable business domains (CPQ, healthcare), CQs accumulate into a persistent requirements base that grounds the knowledge graph. The key finding from Lippolis et al.: when using LLMs to generate ontological structure from CQs, process each CQ independently and merge (Memoryless CQbyCQ) rather than feeding accumulated context — accumulated context distracts the LLM and reduces quality.
- **Intent specification integration** — Now has its own sub-opportunity (O4d) with two solutions (S16c explicit commits, S16d implicit preference extraction). The cross-cutting concern that remains: intent spec updates aren't just an O4d problem — they affect O5 seams (composition with per-session prompts), O1d (verification should flag assumption-driven elements that contradict the spec), and the adaptation layer (persistent preferences feed adaptation rules). The key design question is still open: should every UI modification trigger a candidate intent commit, or only significant ones?
- **[[gentle slope]] in practice** — The slope from "use the generated UI" through "tweak values" to "edit the IR" to "modify the prompt" must be walkable. This isn't one solution — it's a design constraint on all solutions.
- **Notation evolution awareness** — Zhang et al. (2025) frame UI generation as notation design: the system chooses which [[dimensions-of-meaningful-variation]] to foreground and which [[linking-and-grounding-metaphors]] to use. Two implications: (1) the pattern library (S12) should be organised by which dimensions each component foregrounds, not just data type compatibility — this helps the LLM reason about metaphor aptness. (2) User modifications that break established patterns should be treated as potential [[notation-evolution-stages|Stage 2 divergence]] (personal variants worth learning from), not errors to revert. The [[translation-vs-creation-in-AI]] challenge is a long-term architectural constraint: the pipeline should leave room for the component vocabulary to evolve, not hard-code it as fixed.
- **Modality selection** — Andru & Saksena (2025) surface a decision layer *above* pattern selection: which interface container ([[modality-as-task-container]]) should host the generated UI? Task complexity, AI autonomy, and AI reasoning jointly determine whether the output should be a lightweight contextual widget, a rail panel, a full-screen view, or a canvas workspace. [[fluid-modality-transitions]] mean the pipeline's output should be re-hostable across modalities as tasks evolve — a design constraint on the spec format (modality-agnostic abstract specs + modality-specific bindings). Not yet prioritised as an experiment; becomes relevant once multi-view rendering is working.
- **User model architecture (dual-structure)** — The user profile needs two structurally different sub-models: (1) **accessibility/capability** needs → structured taxonomy (OADAPT-style, tree-structured, deterministic adaptation rules), and (2) **interaction preferences** → knowledge items with fluid scope + confidence ([[cross-task-user-knowledge]], InterQuest-style, non-hierarchical, entropy-driven refinement). Attempting a single unified taxonomy for both will either over-structure preferences (forcing users into categories that don't match their actual scope boundaries) or under-structure accessibility needs (losing the deterministic rule-mapping that makes adaptations reliable). This cuts across O4a (preference-based intent resolution), the adaptation layer, and the model evolution loop.

## Suggested experiment sequence

The tree doesn't prescribe a linear order, but dependencies exist. A sensible sequence:

1. **S1 + S2** (O1a) — Two-way binding + accretive overlays. Infrastructure: nothing downstream works without bidirectional data flow. Can be prototyped against json-render directly. S4 (in-place inspection) can ride along cheaply once binding works.

2. **S7, then S8 selectively** (O2a) — IR design. Start with S7 (task-driven data model): write CQs for 3–5 tasks first, then hand-author IRs to answer them. In parallel, test LLM-generated IRs from the same CQs (Memoryless CQbyCQ pattern) to establish whether the hand-authoring step can eventually be automated. Where S7 hits behavioural complexity (state machines, side effects), layer in S8 (concept specs) for those cases only. The CQs produced here become reusable evaluation criteria for downstream experiments (S19, S20). This is the core design problem — it shapes everything else.

3. **S12** (O3) — Pattern library / design knowledge. Once the IR exists, author mapping rules at the component level. Static rules first; constraint-driven (S13) and LLM-selected (S14) are upgrades, not starting points. Defer modality and cognitive-load constraints to after the vertical slice.

4. **S17** (O4b) — Knowledge-grounded generation. Can run in parallel with steps 2–3 since it doesn't need rendering infrastructure.

5. **S15** (O4a) — Intent decomposition. Once the IR and mapping rules exist, test whether the LLM can produce valid IRs from decomposed intents.

6. **S21** (O5) — Vertical slice. Wire it all together for one task. Find the seam failures in the *original* pipeline seams (intent → IR → spec → render → edit → update).

7. **S5 + S5c + S6** (O1b, O1c, O1d) — Pre-gen steering (S5, semantic intermediate layer) + post-gen verification (S5c, Requirements/Assumptions) + scoped editing (S6). These are now in separate opportunities, reflecting the temporal transparency principle. S5 helps users steer *before* generation; S5c helps them verify *after*; S6 is the mechanism for acting on what verification surfaces. Quality-of-experience improvements that matter once the basic loop works.

8. **S24** (O5) — New-seam integration tests. Test the boundaries S21 didn't cover: intent spec ↔ session prompt composition, pre-gen → post-gen mode transition, AG-UI protocol fit. Run after step 7 because it requires the steering/verification layers to exist.

9. **S16c + S16d** (O4d) — Persistent intent specification + usage-derived preferences. Run *after* the vertical slice and verification layers work — requires multiple sessions to test cross-session accumulation. S16c is the explicit mechanism (preference commits with impact analysis); S16d is the implicit mechanism (interaction pattern → preference inference). Low infrastructure cost, high insight value.
