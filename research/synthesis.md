## Current understanding

<!-- Updated after each paper. This section curates concept notes into a coherent model. Link to [[concepts/concept-name]] rather than restating ideas here. -->

Generative UI is not about generating better apps — it's about eliminating the app paradigm altogether. The [[tools-not-apps]] principle reframes the goal: instead of generating a monolithic interface, you're dynamically assembling task-specific tools over a [[shared data layer]].

The pipeline has a core tension at its heart: users express intent in unstructured ways, but the system needs structured data to render useful UI ([[structured vs unstructured tension]]). The LLM's primary job is to bridge this gap — converting vague prompts into structured data models. Everything downstream (UI spec, component rendering) operates on the structured side.

The PushPin prototype's [[json-document-backed-components]] pattern — React components backed by shared JSON documents — is close to what json-render already does. The key difference: DFRP is two-way (components read from and write to the JSON), while json-render is currently one-way (JSON → render). Making it two-way is essential for the feedback loop in the target pipeline.

For the system to be truly malleable (not just generative), users need a [[gentle slope]] from viewing the generated UI, through tweaking values, to modifying the underlying specification and data model. An [[in-place toolchain]] — editing tools embedded within the running interface — is what makes this slope walkable. JELLY's "inspect" tool is a first attempt at this.

How components coexist and communicate ([[UI composition]]) is an unsolved problem even in the most mature malleable software prototypes. PushPin found that too much isolation prevents rich UX; Embark found that deep context sharing enables powerful interactions. This will matter as soon as the generated UI has multiple coordinated views (e.g. a map + a list + a calendar for a dinner party).

**Key distinction**: [[UI composition]] (runtime — how instantiated components coordinate) is separate from [[pattern composition]] (design-time — how patterns build from sub-patterns). Pattern libraries must specify both: how to compose patterns structurally AND how the resulting components should communicate at runtime. A "Search" organism pattern needs composition rules: "Results list selection filters Detail view."

There's a layer above all of this that we need to keep in view, even if we're not building it yet. The LAUI paper (Chin et al.) positions the LLM agent not as a one-shot generator but as a persistent operator — a [[LLM agent UI as abstraction layer]] that sits above the GUI and continuously mediates between user needs and system capabilities. The practical implication: the pipeline we're building isn't just a generation pipeline, it's an [[LLM-operable interface]] that an agent will eventually navigate at runtime. This means every stage (catalog, mapping rules, data model) needs to expose inspectable, modifiable surfaces — not just produce output. The payoff is [[emergent workflow]]: interaction patterns that arise at use-time from the specific user's context, rather than being pre-designed. We don't need to build the LAUI layer now, but designing the engine to be hostile to it would be expensive to undo.

The LAUI paper's deeper re-read surfaces two foundational principles that were implicit before. First, [[high-dimensional-configuration-space]]: any sufficiently configurable system (and the genUI pipeline *is* one) has exponentially many valid configurations. Human designers explore a tiny fraction and package the best as presets/patterns. An LLM agent can navigate the full space at use-time because it has access to the user's actual context. This is the fundamental reason patterns are necessary but insufficient — they cover common regions of the space, not all of it. Second, [[design-time-vs-use-time]]: more information is available at use-time (user goals, preferences, skill, environment) than at design-time. The designer knows the system but not the user; the user knows themselves but not the system. The LLM agent, initialised with system knowledge and able to study the user through interaction, has access to both sides simultaneously. This information asymmetry is the philosophical foundation for the entire generative UI approach — generating at use-time rather than designing at design-time.

**The generation process as navigation axis.** Min et al. (2026) — same lab as JELLY — add a dimension to the [[gentle slope]] that's orthogonal to the existing vertical abstraction ladder. The existing slope runs through abstraction levels: view → tweak values → edit specs → edit models. [[generation-layer-as-customisation-surface]] adds a horizontal axis: the generation timeline itself. Each intermediate stage of generation (Categories → Layout → Content → Style) renders as a partial UI the user can inspect and modify. Rewinding to a layer accesses a different customisation dimension. This means the pipeline's internal stages (task analysis → data model → attribute config → view config → UI spec) aren't just computation — they're potential customisation surfaces. Not all stages should be surfaced (too many checkpoints), so the layer selection is itself a design decision. The paper also finds that different layers naturally use different specification formats (NL for categories, JSON for layout, typed interfaces for content, CSS for style) — reinforcing the view that the intermediate representation question (open design question 1) doesn't have a single answer but a stack of answers at different abstraction levels.

**Pattern-driven transformation** (Seffah & Gaffar) provides the missing mechanism for the upstream pipeline. [[pattern|Patterns]] — proven solutions to recurring problems in specific contexts — become the organizing principle. Instead of the LLM generating UI specs from scratch, it navigates a structured space of transformations using [[pattern-driven transformation]]. The [[model hierarchy]] (Task → Dialog → Presentation → Layout) creates intervention points where different abstractions can be evaluated and refined. [[pattern composition]] means complex UIs are built from reusable molecular patterns, not atomic primitives. Critically, patterns serve dual roles: they're building blocks for models *and* transformation drivers between layers — selecting a task pattern implies which presentation patterns to use downstream.

This shifts the LLM's role: it's not a freeform generator, it's a **pattern instantiation engine**. Select appropriate patterns, bind their variables to the current context, compose them into structures, transform them through abstraction layers. The pattern library becomes a constraint grammar — it defines what's generatable. Combined with json-render's catalog (which defines what's *renderable*), you get complete coverage: patterns handle abstract → concrete [[abstraction-to-concrete mapping]], catalog handles concrete → pixels. (Caveat: the "pattern instantiation engine" framing captures the batch-generation step but may undersell the continuous-evolution step. Alexander's later work on generating systems argues that structure-preserving transformations — iterative, context-sensitive, evaluating the whole after each change — are the actual mechanism, not template selection. The pipeline's feedback loop (`↺ customisation → model evolution → UI update`) is structurally closer to generating systems than to pattern languages. See the [[translation-vs-creation-in-AI]] tension — "pattern instantiation engine" is a provisional label for the generation pass, not the full story.)

Fareedi et al.'s ontology + LLM integration work generalises this into a broader principle: [[knowledge-graph-grounded-generation]]. The LLM should always be querying a structured knowledge store — never generating into a void. Their system (Cypher queries over Neo4j knowledge graphs) showed 15% accuracy improvement from grounding. For the genUI pipeline, each stage has its own knowledge store: pattern library for task analysis, component catalog + constraint rules for spec generation, adaptation rules for personalisation. The LLM's job at every stage is translation (NL → structured query/selection), not creation ex nihilo.

**Two-layer constraint system**: Catalog provides component-level guardrails (which components exist, what props they accept). Pattern library provides semantic guardrails (which patterns apply in which contexts, which components to use within patterns). Example: catalog says "Button is valid"; pattern library says "In Search context, use SubmitButton variant". This gives LLMs structured guidance within the safety boundaries.

**The missing user-facing layer.** Park et al. (CHI '26) expose a problem the pipeline design has largely ignored: the user can't see or control what the LLM is doing. The pipeline so far assumes: user prompt → LLM task analysis → structured spec → rendered UI. But this makes the LLM's interpretation invisible — the user fires a prompt into a black box and gets a complete interface back, with no visibility into which of the hundreds of implicit design decisions were intentional vs. inferred vs. wrong. This creates Norman's [[semantic-drift|gulf of execution]] (users can't articulate what they want) and gulf of evaluation (users can't tell if they got it), and these compound through iteration rather than resolving.

The fix is a [[semantic-intermediate-layer]] — an explicit, inspectable representation between user intent and AI output. Park et al.'s implementation uses [[hierarchical-design-semantics]]: four levels (Product → Design System → Feature → Component) with 15 named semantic slots, vertical relationships (Product goals cascade to Design System choices), and horizontal relationships (within Design System, Visual Mood must cohere with Colour). Users can specify semantics directly, or have NL prompts auto-parsed into slots. Post-generation, [[augmented-semantics]] extract what the AI actually implemented and map it back to the same vocabulary, making deviations visible. Refinement works through [[scoped-semantic-editing]] — explicit semantic diffs rather than conversational re-prompting — which prevents [[semantic-drift]] by bounding each change.

The practical implication for the pipeline: the first LLM touchpoint shouldn't just produce a structured spec internally — it should produce a **visible, editable semantic decomposition** that the user reviews before generation proceeds. The pipeline becomes: user prompt → semantic parse (auto, editable) → user review/correction → pattern-driven transformation → spec → render → augmented analysis → scoped refinement. The semantic layer sits between the user and the pattern engine, making the [[gentle slope]] navigable by showing users *what will cascade* from each edit.

**Intent as a manipulable structure, not a text string.** Kim et al. (CHI 2025) address a problem that sits *upstream* of the semantic layer: the user's prompt itself is opaque. Park et al. made the LLM's design interpretation visible; IntentFlow makes the user's own intent visible — to themselves. The system decomposes a prompt into three levels via [[intent-decomposition]]: Goal (task/domain/topic), Intents (explicit + implicit requirements), and Intent Dimensions (typed parameters with UI controls). Each dimension becomes a [[intent-decomposition|manipulable control]] — a Likert scale for ordinal qualities ("formal ← → casual"), a slider for continuous ranges ("length: 200–2000 words"), hashtags for categorical choices. Users steer generation by adjusting these controls rather than re-prompting.

Two things matter for the pipeline. First, **implicit intent extraction**: the LLM doesn't just parse what the user said, it infers what the task logically requires but the user left unstated. "Build me a task tracker" implicitly needs intents around complexity, collaboration scope, and visualisation style. Making these visible before generation catches wrong assumptions early — a concrete mechanism for bridging [[structured vs unstructured tension]]. Second, **[[intent-output-traceability]]**: after generation, a Linking Module creates bidirectional mappings between dimensions and output elements, so users can see which intents shaped which parts of the result and make targeted adjustments. This is [[augmented-semantics]] at the intent level.

IntentFlow and Park et al. are complementary layers. IntentFlow structures *what the user wants to accomplish* (task intent); Park et al. structures *how it should look* (design semantics). Together they form a two-layer mediation that extends the [[gentle slope]] downward: the user can adjust intent dimensions (zero technical knowledge needed — just opinions) before engaging with design-level semantic slots. The full slope now runs: view → correct user model → **adjust intent dimensions** → tweak values → customise attributes → edit semantic specification → swap patterns → edit specs → edit models.

**Three kinds of intermediate layer, not two.** NeuroSync (Zhang et al., UIST '25) identifies a third transparency layer we hadn't considered. IntentFlow structures the *user's* intent (Goal → Intents → Dimensions). Park et al. structures the *design decisions* (Product → Design System → Feature → Component). NeuroSync structures the *LLM's task understanding* — the subtasks, dependencies, and data flows it inferred from the prompt, externalised as an editable graph before generation. This is the model's interpretation of the task, made visible and correctable.

The diagnostic is sharp: [[bidirectional-ambiguity]]. The user can't express nonlinear intent through linear prompts (user → LLM). The LLM can't communicate nonlinear task logic through opaque code (LLM → user). These compound across turns: each misaligned round makes the next one worse. NeuroSync's task graph breaks the cycle by giving both sides a shared, inspectable, editable representation. Users who saw the graph completed tasks in 1–2 iterations instead of 7–8 — not just because they could correct mistakes, but because they could inspect the full task decomposition *in parallel* rather than discovering problems one-by-one through serial prompt-response cycles.

For the genUI pipeline, this suggests the architecture sketch needs updating. Between intent decomposition and semantic specification, there's a functional decomposition layer: "here's what I'll build" as a task graph the user can inspect and correct before the system commits to UI structure. Whether this justifies a full separate panel (as NeuroSync implements) or can be folded into an enhanced semantic layer is an open design question — but the *principle* (make the model's task interpretation visible) is clearly validated by the 50% task time reduction and 66% fewer LLM calls.

[[intent-aware-simplification]] also introduces a useful pattern for managing complexity: as representations grow, dynamically simplify them relative to the user's current intent focus. Irrelevant branches collapse; relevant ones expand. This is [[semantic-zoom]] driven by intent relevance rather than geometric zoom level, and it could apply to any user-facing representation in the pipeline — the semantic layer, the spec tree, even the rendered UI itself.

**Beyond chat: prompts as interface objects.** Henry Riche et al. (CHI '25) make a move that reframes the entire input side of the pipeline. The papers so far (IntentFlow, Park et al.) improve what happens *between* prompts and output — adding intermediate layers, decompositions, checkpoints. AI-instruments attack the prompt itself, arguing it shouldn't be a text string at all. Instead, prompts should be [[prompt-as-interface-object|reified as persistent graphical objects]] — cards, lenses, brushes, containers — that users manipulate directly. The shift: from a conversation model (type → submit → read → re-type) to an instrumental model (adjust → observe → adjust), where intent objects persist in the workspace alongside generated content.

Three ideas matter for the pipeline. First, [[reflection-in-intent]]: when the LLM decomposes a prompt into [type, value] attribute pairs (Fragments), the user sees their own intent structure externalised — the input-facing mirror of [[augmented-semantics]]. This is conceptually the same as IntentFlow's decomposition but with a different temporal model: IntentFlow structures intent as a pre-generation checkpoint, while Fragments persist as manipulable workspace objects that survive across iterations. Second, [[grounding-by-example]]: users can specify intent by pointing at examples ("like this") instead of describing in words. Fillable Brushes extract semantic attributes from a reference and apply them elsewhere, sidestepping the articulation problem entirely. For UI generation, this means "make it like *that* app" could be a valid input mode — the system extracts structural patterns and design tokens from the reference. Third, spatial scoping (Transformative Lenses) offers a concrete interaction model for post-generation modification: instead of re-prompting the whole UI, the user draws a region and applies a transformation to just that part.

The gentle slope now has a richer texture at the intent end. Below "adjust intent dimensions" sits "manipulate reified intent objects" (Fragments — drag, lock, vary), and below that sits "point at examples" (grounding — zero articulation needed). The slope runs: view → correct user model → **ground from example** → **manipulate intent objects** → adjust intent dimensions → tweak values → customise attributes → edit semantic specification → swap patterns → edit specs → edit models. Each step requires slightly more articulation capability.

**Intent tags: a third path into the pipeline.** Gmeiner et al. (CHI '25) demonstrate that intent doesn't have to flow through either a structured decomposition (IntentFlow: system extracts hierarchy) or persistent workspace objects (AI-instruments: LLM decomposes prompt into Fragments). [[intent-tag-as-micro-prompt|Intent tags]] are a user-driven, bottom-up alternative: atomic [label: value] keyword pairs that the user places on a 2D canvas. The critical insight is that this combines all four properties no other method achieves: open prompt format (free-text tags), system guidance (LLM-generated suggestions), GUI-based manipulation (drop-downs, sliders), and continuous representation (tags persist as spatial objects). The tag collection functions as a lightweight, schema-free semantic specification — three groups (Narrative, Visual Style, Content Sources) parallel Park et al.'s hierarchy but without the fixed slots.

Two ideas from this paper matter beyond the interaction design. First, [[meta-intent-elicitation]]: the system doesn't just execute or mirror intent — it expands it. Tag suggestions, drop-down alternatives, and opposite sliders help users discover dimensions of their task they hadn't considered. Participants reported the system helped them "figure out what they want." This is upstream of [[reflection-in-intent]] (which mirrors existing intent) and upstream of [[intent-decomposition]] (which structures existing intent). Meta-intent elicitation *generates new intent* through interaction. For the pipeline, this means the intent layer shouldn't just accept and structure what the user says — it should proactively suggest what they haven't said, grounded in what it knows about the task type.

Second, [[graduated-ambiguity-tolerance]]: the same interface accepts "Dark and Moody" and "#FF33CC" without forcing one precision level. Users choose how precisely to specify each dimension independently. This resolves the [[structured vs unstructured tension]] pragmatically — not by picking one side, but by accepting a spectrum. For the pipeline, every user-facing input should accept both natural language and structured values, with the LLM bridging the gap.

The tag grounding pattern (content → tags, bidirectional) is also significant. IntentTagger can decompose a text prompt into initial tags ("grounding from text prompt") and extract tags from an existing slide ("grounding from slide"). This means the pipeline's intent layer can work in both directions: intent → generation (forward) and existing content → editable intent representation (reverse). Reverse grounding enables post-generation refinement through the same tag interface used for initial specification.

**Beyond the semantic checkpoint: continuous instrumentation.** Viégas & Wattenberg (2023) push the transparency argument further than Park et al. The semantic intermediate layer is a *single checkpoint* — the user reviews intent before generation. But the system's internal model doesn't freeze after that checkpoint. During interaction, the LLM continues building an [[inferred-user-model]] (demographics, expertise, attitude) and a System Model (is it generating factually or fictionally? how confident is it?) that silently shape every output. The fix is [[parallel-state-display]]: non-conversational visual instrumentation — gauges, indicators, scalar bars — running alongside the primary interface in real time, like a car dashboard. This extends the [[gentle slope]] *downward*: below even value tweaking, users can correct the system's assumptions about them ("you think I'm a novice — I'm not"). The key distinction from [[context-driven adaptation]]: OADAPT treats the user profile as a declared *input*; the inferred user model is what the system *believes*, which may be wrong and needs to be surfaceable. For the pipeline, this means intermediate representations (semantic parse, task model, user assumptions, confidence scores) aren't just internal computation — they're the data source for a user-facing monitoring layer.

**Adaptation operationalised.** Jerry et al. (2025) take the OADAPT framework from theory to implementation, and in doing so sharpen a key architectural principle: [[content-structure-adaptation-split]]. Structural adaptation (contrast, layout, font size, modality switching) is fully specifiable by standards and handled by deterministic rules — no LLM needed. Content adaptation (plain language simplification, pictogram generation, cognitive load reduction) requires judgement and uses the LLM — but with [[adaptation-quality-gates]] (readability scoring, semantic fidelity via NLI, factual consistency) that verify the output before rendering. This is the [[programmable-router]] pattern applied to adaptation: route each adaptation task through the cheapest reliable mechanism, escalate to LLM only when rules can't handle it.

The other significant contribution is [[normative-grounded-adaptation]]: every adaptation traces to a specific accessibility standard clause via Derived Accessibility Requirements (DARs). This isn't just good practice — it makes the adaptation layer *auditable*, which matters for regulated domains (healthcare, government, EU accessibility directive). For the pipeline, it means adaptation rules should carry metadata (which standard, which clause, which user need), not just implement behaviour.

Together with OADAPT's theoretical framework, we now have a reasonably complete picture of the adaptation layer: user profile + environment → rule activation (many-to-many via adaptation modes) → structural adaptation (deterministic) + content adaptation (LLM + quality gates) → adapted spec. The [[content-structure-adaptation-split]] also connects to [[ai-attribute-reformulation]] — content adaptation at the accessibility level is structurally the same operation as per-attribute reformulation at the data level: the LLM transforms content while leaving UI structure alone.

**Adaptation as optimisation, not just rules.** Stefanidi et al. (IEEE Access 2022) reveal that sequential adaptation rules have a structural limitation: they can't handle trade-offs between competing elements. When screen space is limited and multiple components vie for visibility, the question isn't "should this component adapt?" but "given all constraints, what's the best overall configuration?" [[optimisation-based-ui-adaptation]] reframes adaptation as a combinatorial optimisation problem — jointly selecting *what* to show, at *what level of detail*, and *where*, subject to constraints including [[cognitive-load-bounded-display]] (a stress-dependent cap on total visible elements, grounded in Miller's law). The SA scoring mechanism — SWRL rules computing continuous appropriateness values for each component given the current context — replaces binary show/hide rules with a gradient. The optimiser then maximises total value subject to constraints, handling trade-offs that rule chains can't express (e.g. showing a lower-detail version of a high-priority element because the full version would collide with another high-priority element). For the genUI pipeline, this suggests the adaptation layer should have two mechanisms: rule-based adaptation for independent modifications ([[content-structure-adaptation-split]] — contrast, font size, LoD per component), and optimisation-based adaptation for interdependent decisions (which subset of components to display given limited space and cognitive capacity). The [[programmable-router]] pattern applies here too: use rules when adaptations are independent, escalate to optimisation when they interact.

**Critical realisation:** Modern [[design systems as pattern libraries]] (Material UI, Radix, Shadcn, Ant Design) already implement everything the pattern-driven approach describes. Component libraries are catalogs. Atomic design (atoms → molecules → organisms) is pattern composition. Design tokens are abstraction layers. Documentation describes usage patterns. Instead of building pattern libraries from scratch, use design systems as the foundation — their documentation becomes LLM training data, their components become the catalog, their composition patterns become the pattern library. This bridges academic MBUI theory with practical, production-ready implementation.

**Architectural detail**: Catalogs need semantic metadata linking components to patterns they implement. A SearchInput component should tag itself: `implements: ["Search.input", "MultiValueInput"]`. This enables reverse lookup — given a pattern, find matching catalog components. Without this, patterns and catalog remain disconnected.

**Ontology-driven UI** (Nunes et al.) reveals a third approach to domain-to-UI mapping that sits alongside patterns and LLM inference. [[ontology-driven UI generation]] uses formal ontologies (OWL/RDF) as the structural backbone — class hierarchies, semantic relationships, and formal cardinality constraints parsed at runtime and mapped directly to UI elements. The mapping mechanism is [[constraint-driven component selection]]: deterministic rules that convert ontological constraints into specific component choices (`only` → dropdown, `some` → add button, `min 1` → required field, `exactly x` → fixed-count inputs). No LLM needed for leaf-level component decisions.

**Three-layer mapping architecture** emerges from combining Seffah's patterns with Nunes's constraint rules:

1. **Patterns** handle macro structure — what *sections* of UI to create (Search panel, Results list, Detail view). The LLM selects and instantiates these.
2. **Constraint rules** handle micro structure — what *component* for each field within those sections. Deterministic, based on data types and cardinalities. No LLM needed.
3. **LLM inference** handles edge cases — ambiguous mappings, novel task structures, aesthetic/UX decisions that neither patterns nor rules cover.

This is powerful because it pushes the LLM's responsibility *upward*. Instead of the LLM deciding both "should this be a search UI?" AND "should the location field be a dropdown or a text input?", it only handles the first question. The second is handled by constraint rules reading the data schema. Fewer LLM decisions = more predictable output.

The ontology paper also demonstrates that formal ontologies output JSON intermediate representations strikingly similar to json-render specs — properties, related classes, subclasses, cardinalities, all in a parseable format the React frontend renders dynamically. This validates [[specification-based rendering]] as a general principle: whether the spec comes from an LLM, a pattern transformation pipeline, or an ontology parser, the rendering side works the same way.

**Configuration as design space navigation.** Kumbang (Asikainen et al., 2007) contributes a reframe that cuts deeper than its product-family origins suggest. A product family model doesn't describe a single product — it describes a [[configuration-model-as-design-space|space of valid products]], with variation points as dimensions and constraints carving away illegal regions. A specific product is a single point in this space. The design task shifts from "build this thing" to "define the space, then navigate to a point." For generative UI, this reframes what the pipeline's output should be: not a single UI spec but a **configuration model** — a constrained space of valid interfaces for the user's task, with the initial rendering being a sensible default point and user customisation being navigation within the space. The constraint solver (or inference engine) handles consistency, so users can make local changes without violating global rules.

Kumbang also formalises a [[feature-component-duality]] that maps onto the pipeline's existing intuitions. Features (user-facing capabilities: "I want task filtering") and components (implementation building blocks: "FilterBar with status enum") are modelled as separate type hierarchies linked by implementation constraints. This is the same structural pattern as DuetUI's [[task-interface-duality]], but with formal constraint language. The duality suggests the intermediate representation needs two faces — a feature face the user understands and a component face the system builds from — with explicit, inspectable bridging rules.

**Key question the ontology approach raises**: does the pipeline need a formal ontology as intermediate representation? Full OWL is heavy (requires ontology engineers), but the *principle* — enriching the data model with semantic constraints that drive deterministic component selection — could work with lighter-weight schemas. JELLY's task-driven data model is essentially a lightweight ontology: entities with attributes, relationships, and constraints. If those constraints include cardinality and type information, the [[constraint-driven component selection]] rules can apply directly. The LLM's schema generation step just needs to include constraint metadata, not just bare types.

**Missing pipeline input: user context.** OADAPT (Freitas & Barcellos) reveals that the pipeline is incomplete without [[context-driven adaptation]]. The current sketch takes user intent ("what to build") + domain model ("what the data looks like") → UI. It should also take user context ("who this is for") → adapted UI. OADAPT models this through a User Profile Ontology covering disabilities, experience level, preferences, language, age — each driving specific UI adaptations (colourblind → recoloured elements, low vision → high contrast, novice → progressive disclosure).

The architecturally interesting bit: adaptation rules form a **separate layer**, not something embedded in component logic. OADAPT's four-layer architecture (UI / Application / Reasoning engine / Semantic layer) keeps adaptation knowledge decoupled from both the domain model and the UI components. The reasoning engine takes (user profile + domain model) as inputs, produces adaptation directives.

For the genUI pipeline, this splits into two strategies depending on the type of adaptation:
- **Accessibility adaptations** (WCAG compliance, disability support) → deterministic post-processing rules. You want reliable, auditable behaviour here, not LLM guesses.
- **Preference/experience adaptations** (density, complexity, defaults) → can be handled as LLM context. "Generate for an expert user" vs. "generate for a novice" are legitimate prompt parameters.

OADAPT also introduces the **ontology network** concept — not one monolithic model but multiple interconnected ontologies (domain, user profile, UI elements, adaptation system) that compose and evolve independently. For the genUI pipeline, this suggests keeping schemas modular: domain schema + user profile schema + component catalog + adaptation rules, loosely coupled rather than fused into one structure. Whether these need to be formal ontologies (as OADAPT proposes) or simpler structured schemas (as seems more practical for LLM-driven generation) remains an open question.

The conceptual/operational distinction in OADAPT maps neatly onto the existing architecture: **conceptual** = pattern library + user profile schema (reusable design knowledge, application-independent); **operational** = catalog + constraint rules + adaptation rules (machine-readable, runtime artifacts).

**Concrete adaptation mechanics** (from the OADAPT specification paper). The companion specification fills in the detail the doctoral overview left abstract. Key additions: (1) **Adaptation modes** as an intermediate abstraction — 14 UI Customisation Types (Dark Mode, Contrast Mode, Font Mode, Voice Command Mode, Screen Reader Mode, etc.) that sit between user traits and concrete CSS/component changes. The many-to-many relationship (multiple disabilities → same mode, one disability → multiple modes) is mediated by formal Customisation Recommendations. (2) **30 WCAG-derived rules** mapping disability types to mode combinations, expressed in first-order logic but functionally equivalent to a lookup table. (3) **Environment context** (ContUsO) as a separate trigger source — luminosity, noise, connectivity, geolocation, time of day can activate adaptations independently of user profile. (4) **Mutual exclusion constraints** between modes (Desktop ⊕ Mobile, Light ⊕ Dark, exactly one experience level).

The specification also provides a formal **UI component taxonomy** (UISCO) that classifies the target space into Media, Layout, Alert, Form, and Status Indicator categories — a classification that converges almost exactly with how practical component libraries (Radix, MUI) organise themselves. This convergence suggests the categorisation reflects genuine structure in the UI domain rather than being an artefact of formal ontology engineering.

**Assessment after two OADAPT papers:** The *knowledge content* is valuable — the disability taxonomy, adaptation rules, component classification, and environment model are useful regardless of whether they're encoded as formal ontologies or simpler schemas. The ontological formalism (UFO grounding, powertype relationships, competency-question verification) adds rigour but also ~40 pages of specification for a single adaptive social network. For the genUI pipeline, the practical takeaway is the rules and taxonomies themselves, implementable as simple JSON schemas + if-then rules without the OWL/UFO overhead.

**Varv** (Borowski et al., 2022) pushes [[specification-based rendering]] to its logical extreme: [[software-as-data-structure]]. Not just the UI but the entire application — state schemas, state transition rules, event bindings, view templates, data storage mappings — is a declarative JSON data structure that the runtime interprets. The payoff is toolability: because the program is data, you can build generic inspection, editing, and composition tools that work on any application. Varv's data inspector and view inspector are concrete implementations of the [[in-place toolchain]] we've been theorising about.

Three ideas from Varv shift the model:

1. **[[accretive-extensibility]]** — software modification happens purely by addition. New concept definitions layer on top of existing ones; the runtime merges them. Nothing is ever edited or deleted. For the genUI pipeline, this reframes model evolution: instead of regenerating or editing specs, user customisations should be **overlay layers** on top of generated base specs. This makes regeneration safe (the base can change without destroying user modifications) and customisations portable (overlays can be shared independently).

2. **[[abstract-concrete-separation]]** — concept definitions split into abstract (semantic events: "item completed") and concrete (modality bindings: "checkbox clicked"). The abstract layer is reusable across platforms; only the concrete layer changes when you retarget from desktop to mobile to AR. This maps cleanly onto the [[model hierarchy]]: task and dialog models are abstract; presentation and layout models are concrete. For the pipeline, it suggests a two-pass generation: LLM produces abstract concepts (entities, relationships, valid actions); deterministic rules bind them to concrete components.

3. **[[concept-as-composition-unit]]** — a "concept" bundles state (schema), behaviour (actions), and triggers into a named, composable unit. Unlike UI components, concepts can be purely abstract ("assignable", "filterable") and composed via extension operators (inject, join, omit, pick). This is a higher-level unit than patterns — it captures *functionality*, not just *UI structure*. The board game toolkit case study demonstrates: domain-specific concept libraries enable rapid creation of multiple applications from shared abstractions.

**Déjà Vu** (De Rosso & Jackson, MIT) provides a contrasting implementation of [[concept-as-composition-unit]] that sharpens the composition question. Where Varv shares everything (centralised state, no encapsulation), Déjà Vu shares nothing (each concept is a self-contained full-stack service). Integration happens through [[declarative-concept-binding]]: a template language that wires concepts via dataflow bindings, [[identity-based-data-integration]] (shared IDs, not shared data), and [[transactional-composition]] (declarative transaction wrappers for atomic cross-concept actions). The template IS the application architecture — ~400 lines that select and wire generic concepts from a [[concept-catalog]] of 18 reusable full-stack modules.

The **concept catalog** idea is significant for the pipeline. Déjà Vu's catalog (Authentication, Comment, Scoring, Task, Transfer, etc.) sits *above* the component catalog: it describes what functionality the app needs, not what widgets to render. The LLM's task analysis step could map to concept selection: "build an event planner" → select Event, Schedule, Group, Geolocation from the catalog. This decomposes the generation problem into three steps: **select** concepts from catalog → **compose** via binding template → **map** to UI components. It's more structured than jumping from prompt to json-render spec.

The Varv/Déjà Vu comparison reveals a **composition spectrum** with real architectural consequences. Shared state (Varv, JELLY) makes cross-concept features trivial but reasoning hard — any concept can affect any other. Explicit bindings (Déjà Vu) keeps the data flow visible and reasoning tractable, but cross-concept features require manual wiring. For LLM generation, shared state is easier to produce (one schema); binding templates are harder to produce but more predictable. A2UI's data/component separation (from the industry scan) suggests a middle path: shared data model for state, explicit bindings for coordination.

**Assessment:** Varv provides the missing model for *how generated interfaces should be modified*. The pipeline currently assumes a waterfall: generate → render → (somehow) evolve. Varv shows a concrete alternative: generate a base set of concept definitions → user layers modifications accretively → runtime merges everything → changes appear live. The open question is whether this model works with LLM generation — can an LLM produce concept definitions (not just UI specs) and can it produce overlays (not just complete regeneration)?

**Revised position on concepts (post Kodless, WYSIWID, Palantir):** Three additional papers on Daniel Jackson's concepts — Kodless (Voronin, 2024), WYSIWID (Meng & Jackson, Onward! '25), and concept-centric development at Palantir (Wilczynski et al., 2023) — sharpen the picture considerably. Kodless shows that concept-named prompts produce better LLM output than feature descriptions ([[concept-spec-as-generation-checkpoint]]), but the LLM still generates full-stack code, not concept-structured output. WYSIWID introduces [[synchronisation-as-behavioural-rule]] — declarative when/where/then rules for composing concepts — which is a cleaner mechanism than Déjà Vu's template bindings. Palantir reveals [[concept-entropy]]: at scale (~500 concepts), concept inventories accumulate duplication, boundary confusion, and naming drift unless actively maintained.

The key revision: concepts should **not** be a primary pipeline stage. Déjà Vu's select→compose→map decomposition (line 133 above) treats concepts as the mandatory intermediate between task analysis and data model. This is too heavy for most cases. Most UIs can be composed from patterns + components (structural composition) without needing named behavioural specifications. Concepts become important when **state transitions and side effects create behavioural complexity that patterns can't express** — authentication flows, scoring systems, approval workflows, real-time collaboration. These are occasional but critical.

The revised architecture has **two tiers of composition**: (1) Structural composition (patterns + components) as the default, covering most generation. (2) Behavioural specification (concepts) added on-demand when structural composition proves insufficient. The [[concept-catalog]] shifts from a mandatory pipeline stage to a **knowledge resource** in the MCP layer — consulted when the LLM needs a behavioural vocabulary, not invoked on every generation pass. See [[concept-as-behavioural-annotation]] for the detailed position.

The architecture should be **hospitable to concepts before any exist**: clean separation of data model, component tree, and an initially empty behavioural rule layer. When a concept is needed, it slots into the rule layer without restructuring. Bottom-up growth: useful generated concepts get promoted to the catalog; the catalog grows from actual need, not anticipated requirements. Three resulting design modes: structural composition (most of the time), pattern selection (frequent), behavioural specification (occasional but critical).

**Malleable Overview+Detail** (Min, Chen, Cao & Xia, 2025) and **Meridian** (Min & Xia, 2025) — from the same research group as JELLY — zoom into a specific, high-frequency pattern (overview+detail, found in 83% of information-seeking apps surveyed) and ask: what does it take to make *this* pattern malleable? The answer introduces a new abstraction level we hadn't considered: [[fluid-attributes]]. Instead of customising components or specs, users customise *data attributes* — which ones appear, in what format, in which view, with what AI-driven reformulations. The attribute is the natural unit of customisation because it maps to the user's vocabulary ("show me the price per night") rather than the implementation's vocabulary ("modify the card component's props").

This fills a concrete gap in the [[gentle slope]]. We had: view → tweak values → swap patterns → edit specs → edit models. Between "tweak values" and "swap patterns" there was a cliff — the user had to jump from modifying data to understanding UI structure. [[fluid-attributes]] sits in this gap: more powerful than value editing (you can add entirely new attributes, including AI-derived ones), less demanding than pattern manipulation (no structural understanding needed).

Meridian's declarative specification is architecturally interesting because it introduces a **four-layer config** — DataConfig → AttributeConfig → ViewConfig → LayoutConfig — that's neither json-render's flat component spec nor the model hierarchy's four-model cascade. The attribute config layer mediates between raw data and view presentation, and it's where the LLM adds the most value: deciding that raw review text should be reformulated into a sentiment badge, or that price and comparable listings should be synthesised into a "value score." This is [[ai-attribute-reformulation]] — using the LLM not for whole-UI generation but for per-attribute data transformation. A different, more granular role than spec generation, with different timing (runs per data item at fetch time, not once at design time).

Critically, Meridian's end-user customisations are **spec overlays** — they modify the attribute/view config accretively, never touching the developer-defined base. This validates [[accretive-extensibility]] in a production React framework, not just Varv's research prototype. And the overlay model is naturally attribute-scoped: "add distance to overview" is an overlay on ViewConfig; "show price as per-night" is an overlay on AttributeConfig. Clean, reversible, composable.

**New pipeline insight**: the LLM should have **two touchpoints**, not one. (1) Spec generation at design time — task analysis, pattern selection, UI structure. (2) Attribute reformulation at data time — per-item semantic transformation of data values. These use different prompts, different models (reformulation could use a smaller, cheaper model), and different caching strategies. The pipeline sketch needs updating.

**The runtime connection problem.** AG-UI (the Agent–User Interaction Protocol) exposes something the pipeline design had been treating as out-of-scope: the generated UI needs a persistent, bidirectional runtime connection to the agent, not just a one-shot generation pipeline. The feedback loop (rendered UI ↺ end-user customisation → model evolution → UI update) requires the agent to observe user actions and the frontend to render agent updates — continuously, not in discrete request-response cycles. AG-UI's [[event-driven agent-UI protocol]] provides the concrete mechanism: typed event streams with two core patterns — Start-Content-End for incremental delivery (streaming specs, streaming tool call arguments) and Snapshot-Delta for state synchronisation ([[shared data layer]] via JSON Patch RFC 6902).

Three AG-UI ideas sharpen the pipeline architecture. First, [[two-step generative UI]]: the agent specifies *what* UI is needed (description + data + output schema) and a dedicated generator produces *how* — validating the separation between task analysis (reasoning LLM) and spec generation (specialist LLM/generator) that the pipeline already assumes, and suggesting the step-1 output could be the [[semantic-intermediate-layer]] or pattern selections rather than a freeform description. Second, [[frontend-defined tool execution]]: tools are owned by the frontend, not the agent. The frontend declares what operations are available (as JSON Schema), the agent requests execution, the frontend runs them locally. This inverts agent autonomy and provides a runtime-configurable guardrail layer — the [[guardrailed generative UI]] principle applied to actions, not just output. Third, [[shared data layer]]: bidirectional state sync via snapshots and JSON Patch deltas provides the concrete mechanism for two-way binding. This answers the long-standing open thread about spec evolution — use deltas for incremental changes (user edits a value → patch), snapshots for major changes (user switches task model → full regeneration).

The AG-UI protocol also clarifies the relationship between the three layers of the emerging agent stack: MCP connects agents to tools/data (backend), A2A connects agents to each other (orchestration), AG-UI connects agents to users (frontend). The genUI pipeline's pattern library, component catalog, and data model are MCP-layer resources; the user-facing semantic layer, inspection tools, and rendered UI are AG-UI-layer concerns. Keeping these boundaries clean means the pipeline engine can serve both human users (via AG-UI frontend) and agent operators (via MCP/A2A), supporting the [[LLM-operable interface]] vision without architectural changes.

**Co-generation as the interaction paradigm.** DuetUI (Xu et al., 2025) closes a major gap: the pipeline described everything *above* the runtime connection (intent → spec → render) and *below* it (AG-UI events, state sync), but was vague about the interaction paradigm that sits in between — how do the human and agent actually collaborate moment-to-moment? DuetUI's answer is the [[bidirectional-context-loop]]: the agent generates UI structure (downward), the user's manipulations of that UI feed back as implicit context (upward), and a shared action history enables continuous alignment without explicit re-prompting. The interface itself is the communication medium, not chat.

This resolves several tensions that earlier papers surfaced. [[bidirectional-ambiguity]] (NeuroSync) diagnoses the problem of misalignment compounding across turns — but proposes a pre-generation fix (editable task graph). The bidirectional context loop is a complementary *runtime* fix: instead of perfecting the upfront specification, it creates a continuous correction channel through the interface. The AG-UI protocol provides the plumbing (events, state sync); the bidirectional context loop provides the interaction semantics (what those events *mean* for collaboration).

DuetUI also introduces four ideas that sharpen the pipeline's user-facing design. [[tangible-agency]] — embedding agent capabilities as directly manipulable controls (sliders, buttons, pickers) within the generated interface — resolves the gulf of execution that DuetUI's formative study found (11/12 participants saw the AI as a "black box"). This validates [[prompt-as-interface-object]] with real user data: participants overwhelmingly preferred structured controls over conversational prompting, with 15/24 reporting reduced prompting burden. [[task-interface-duality]] — maintaining a strict hierarchical correspondence between task decomposition (Task → Subtask → Data) and interface description (Navigation → Page → Component) — gives the pipeline a structural principle for how the generated spec should relate to the task model. [[staged-co-generation]] — a six-stage temporal workflow (Define → Empathise → Plan → Explore → Refine → Duet) — adds a temporal dimension to the [[gentle slope]]: the system progressively elicits more detail across stages rather than demanding upfront specification. And [[adaptive-autonomy]] — dynamic control allocation shifting with user expertise and task familiarity — extends [[context-driven adaptation]] from UI presentation to collaboration dynamics.

The user study (N=24, within-subjects vs. Google Stitch) provides the strongest empirical support for the co-generation paradigm: significantly higher usability (SUS: 73.65 vs. 63.5, p=.002), task satisfaction (p=.005), and AI satisfaction (p=.001). Crucially, participants overwhelmingly preferred iterative dialogue over one-shot generation — "I don't expect it to get everything right in one go... The best thing is that it can iterate quickly" — and valued predictability and structural consistency over visual novelty. This validates a core principle: generative UI should prioritise **predictable, incrementally refinable output** over impressive one-shot generation.

Two caveats. First, DuetUI used simulated data — real API integration would add latency and error handling complexity. Second, the trust findings are sobering: a single incorrect data point caused "collapse of trust" that was "very hard to win back" (P14). Hallucination isn't just a quality problem — it's a collaboration-destroying event. This strengthens the case for [[knowledge-graph-grounded-generation]] and [[adaptation-quality-gates]] as non-optional infrastructure.

**Interaction as a dimension of intelligence, not an interface layer.** Ye et al. (2025) provide the philosophical capstone to the co-generation argument: [[interaction-as-intelligence]]. The pipeline isn't a generation engine that minimises human involvement — it's collaboration infrastructure where intelligence emerges through the interaction itself. This is stronger than the DuetUI claim (that co-generation is better than one-shot). It says intermediate layers ([[semantic-intermediate-layer]], [[intent-decomposition]], [[externalised-LLM-understanding]]) aren't UX polish or debugging aids — they're where the system *thinks*. The user reviewing a semantic parse is the combined human-AI system performing cognition, not a human checking AI homework.

The empirical contribution sharpens [[adaptive-autonomy]]: [[dynamic-cooperation-willingness]] shows users naturally oscillate between hands-on and hands-off modes in a predictable six-phase pattern. Hands-on at clarification and intervention points, hands-off during mechanical reasoning and summarisation. For the pipeline, this means not all intermediate checkpoints need equal attention — intent decomposition and final review should default to hands-on; pattern transformation and attribute reformulation should default to hands-off with transparency (show what's happening, don't demand decisions). [[usage-as-annotation]] provides the mechanism for the model evolution loop: normal interaction (not explicit feedback) implicitly trains the system's preferences, closing the `↺` without adding feedback burden.

**A design language for the customisation layer.** The pipeline's `↺ End-user customisation (NL + direct manipulation) → Model evolution → UI update` loop names both input modalities but doesn't specify *how* they should combine. Shen et al. (CHI '26) provide the missing vocabulary: [[prompt-interaction-synergy]] frames text and interaction as fundamentally complementary (prompts carry intent, interactions carry specificity), and the [[augmented-instruction]] (Aug) is the composite input GenAI actually receives — assembled from text (T → Aug), interaction-derived information (I → Aug), and artifact context (A → Aug). The 12 atomic paradigms organised into a [[paradigm-graph-as-design-language]] (pre/post invocation × prompt-only/artifact-grounded) serve as a design menu for the customisation loop. Table 3's cheat sheet gives direct guidance: need structured task decomposition → P2 (interactive prompt organisation); need transparent intermediate reasoning → P6 (AI-driven prompt decomposition); need persistent controls for iteration → P8 (generative artifact control widgets). The paradigm graph formalism also connects existing concepts: [[tangible-agency]] maps to P7/P8, [[intent-decomposition]] maps to P6, [[grounding-by-example]] maps to P3/P4/P9–P12. And the graphs add a new dimension to the [[gentle slope]] — users progress through increasingly complex paradigm graph structures (from P5's lightweight AI suggestions through P1's prompt editing to P12's full artifact-grounded refinement) as their engagement deepens.

**Transparency is not monotonically good — and temporal context matters.** Grunde-McLaughlin et al. (Microsoft Research, 2026) deliver the strongest empirical challenge to the vault's accumulating assumption that more visibility into the pipeline is always better. Three studies on agent verification show that *how* a trace is structured matters more than how much is shown. [[outcome-oriented-verification]] — decomposing the agent's output into Requirements (what was asked) and Assumptions (what it decided unilaterally) — achieved the best error detection (77.14%). But [[process-induced-overreliance]] is the cautionary finding: showing users a detailed, reasonable-looking step-by-step process (Flowchart design) produced the *worst* error detection (39.13% on incorrect tasks). The process narrative short-circuited critical evaluation — "if the steps look sensible, the result must be correct."

The implication for the pipeline's many intermediate layers (intent decomposition, task graph, semantic specification, pattern selection) is a temporal design principle: use **process-oriented transparency before generation** (where the user can redirect) and **outcome-oriented transparency after generation** (where the user needs to verify). NeuroSync's task graph and IntentFlow's dimension controls are valuable *pre-generation* because they let users steer; but as *post-generation* verification, they risk [[process-induced-overreliance]]. Post-generation verification should decompose the output into "here's what you asked for" and "here's what I assumed" — the Requirements/Assumptions pattern. The false confidence finding (Hedges' g: 0.85 — users with better tools were more confident when wrong) tempers optimism about verification checkpoints generally: structured engagement isn't enough; it must be *analytically* structured ([[cognitive-engagement-for-reliance]]).

**Objectives can be inferred, not just specified.** Lam et al. (CHI '26) demonstrate that the per-session prompt doesn't have to come from the user at all — [[just-in-time-objective-induction]] derives objectives passively from observed context (a screenshot, a document). The system watches, hypothesises, and presents objectives for review. This sidesteps the articulation problem ([[bidirectional-ambiguity]]) entirely: instead of structuring what users say (IntentFlow, Intent Tags) or making prompts manipulable (AI-Instruments), JIT objectives skip prompting altogether. The [[generate-then-rank-with-objectives]] architecture — applying the induced objective to both generation and evaluation — achieves 66–86% win rates over unsteered baselines with trivial implementation (objective prepended to existing prompts). For the pipeline, this suggests the pre-generation phase could start *before* the user types anything: observe their context, induce candidate objectives, and present them as a starting point for the intent decomposition cascade. JIT objectives and persistent intent specs ([[intent-specification-as-common-ground]]) complement rather than compete: persistent specs encode stable preferences across sessions, JIT objectives capture ephemeral in-the-moment goals. The Poppins system (Poppins-tools) also demonstrates [[objective-driven-tool-generation]] — generating complete functional interactive software from objectives, not just text or static layouts. This is the closest existing system to the full generative UI vision, though it lacks the persistent data model, component catalog constraints, and accretive modification the pipeline requires.

**The pipeline has four inputs, not two.** The early narrative assumed: user prompt (per-session intent) + domain model (what the data looks like) → UI. OADAPT added user context as a third. SemanticCommit (Vaithilingam et al.) reveals a fourth that subsumes the per-session prompt: a **persistent intent specification** — a human-readable document (CLAUDE.md, cursor rules, or equivalent) that accumulates the user's preferences, conventions, and constraints across sessions. This is [[intent-specification-as-common-ground]]: not a per-interaction prompt but a living coordination artefact between human and AI. The pipeline's input is now: persistent intent spec (cross-session) + per-session prompt (this task) + domain model + user context → generation. Critically, the feedback loop (`↺`) doesn't just update the UI — it should also surface candidate updates to the intent spec, with [[impact-analysis-before-generation]] (show the blast radius of a preference change before committing it). Users overwhelmingly preferred impact-first workflows: 6/12 always started with conflict analysis, never delegating to global AI changes. The additional review step did not increase perceived workload — control offset cost.

**The user model is a constructed knowledge base, not an extracted snapshot.** Early sections treat the [[inferred-user-model]] (Viégas & Wattenberg) as something to extract from the LLM's opaque internals via structured prompting. InterQuest (Mei et al.) provides a better architecture: build a separate [[cross-task-user-knowledge]] base from interaction data, with each preference item carrying content + scope + confidence. The scope finding is important — preference boundaries are fluid and overlapping, not tree-structured, which challenges any taxonomy-based approach to user modelling (including OADAPT's hierarchical User Profile Ontology for preference-level data; OADAPT's disability/accessibility taxonomy is fine because those categories *are* tree-structured). [[uncertainty-driven-elicitation]] provides the refinement loop: Shannon entropy identifies which uncertainties to resolve through proactive questioning (ask where p ≈ 0.5, not where p ≈ 0 or 1). This also sharpens the [[alignment-cost-tradeoff]]: the "quick generate" vs. "guided generate" distinction should be dynamic — the system surfaces checkpoints based on knowledge entropy, not a user-selected mode switch.

**The protocol stack is infrastructure, not plumbing.** The pipeline describes what to generate and how to refine it; but the *runtime mechanism* through which generation, interaction, and data access happen is a structural concern, not an implementation detail. Three protocol layers have emerged: **MCP** connects agents to tools and data (backend integration — the pattern library, component catalog, data model, and external APIs are MCP-layer resources), **AG-UI** connects agents to users (frontend — event-driven bidirectional streams carrying specs, state diffs, and tool calls), and **A2A** connects agents to each other (orchestration). The pipeline engine sits between MCP (below) and AG-UI (above). This separation matters because the same engine can serve human users (via AG-UI frontend, with all the intermediate layers and gentle slope) and agent operators (via MCP/A2A, machine-to-machine, skipping the human-facing layers), supporting the [[LLM-operable interface]] vision without architectural changes. AG-UI's [[frontend-defined tool execution]] adds a runtime guardrail layer: the frontend declares what operations are available, the agent requests execution, the frontend runs them locally. This inverts agent autonomy and makes the guardrail boundary user-configurable.

## Architecture sketch

The target pipeline (informed by JELLY as north star, with semantic + intent layers, protocol stack, and temporal transparency principle):

```
INPUTS:
  Persistent intent specification (cross-session: CLAUDE.md / cursor rules / equivalent)
  + Per-session prompt (this task's intent)
  + User context (profile, preferences, accessibility needs, environment)
  + Domain model / data sources (via MCP)

PRE-GENERATION (process-oriented transparency — user steers):
  → Intent decomposition (LLM: NL → Goal + Intents + Intent Dimensions)
    → Modality inference (task complexity × autonomy × reasoning depth → container type)
      → Intent + modality review (user adjusts dimension controls; confirms/overrides container)
        → Semantic parse (LLM: intents → structured design semantic slots)
          → Semantic review (user inspects/edits Product/DesignSystem/Feature/Component)
            → Task analysis (LLM touchpoint 1: semantic slots + patterns → spec generation)
              [modality constrains pattern selection: contextual → lightweight only;
               canvas/full-screen → full library; cognitive load bound per modality]
              → Task-driven data model (schema + dependencies + data)
                → Attribute configuration (formatters, display types, AI reformulations)
                  → View configuration (which attributes in which views)
                    → UI specification (modality-agnostic abstract spec + state)
                      → Adaptation rules (user context → spec modifications)

GENERATION + DATA-TIME:
  → Modality binding (abstract spec → container-specific layout + density limits)
    [cognitive load bound applied: contextual ≤5 elements, full-screen ≤9, per Miller's law]
  → Rendered UI (component library, within modality container)
  → LLM touchpoint 2: per-item attribute reformulation (runs at data-fetch time, not design time)

POST-GENERATION (outcome-oriented transparency — user verifies):
  → Requirements/Assumptions decomposition (what was asked vs. what was inferred)
  → Augmented semantics (extract implemented semantics, compare to input)
  → Intent-output traceability (link dimensions ↔ output elements)
  ↺ Scoped refinement (semantic diffs OR dimension adjustment + code anchor)
    → Spec overlay → re-render
  ↺ Modality transition (user/system shifts container as task complexity evolves)
    → Rebind abstract spec to new container (state preserved, density re-evaluated)
  ↺ Intent spec update candidates (surface implicit preference changes for user review
    with impact analysis before commitment)

PROTOCOL STACK:
  MCP layer (backend): pattern library, component catalog, concept catalog (knowledge resource, not pipeline stage), data model, external APIs
  AG-UI layer (frontend): event-driven bidirectional agent ↔ UI connection
    StateSnapshot / StateDelta (JSON Patch) for state sync
    Frontend-defined tools for agent actions (runtime-configurable guardrails)
    Start-Content-End streaming for incremental delivery
  A2A layer (orchestration): agent-to-agent coordination (future)
```

**Note on checkpoint density:** Not all pre-generation steps demand user attention equally. [[dynamic-cooperation-willingness]] shows users oscillate between hands-on (clarification, intent review) and hands-off (pattern transformation, attribute config) phases. [[uncertainty-driven-elicitation]] suggests surfacing checkpoints dynamically based on knowledge entropy — demand attention where the system is most uncertain, offer transparency-without-interruption where it's confident. The "quick generate" path collapses pre-generation to prompt → render; the "guided generate" path exposes all intermediate layers. The system should choose based on task complexity + user familiarity + knowledge entropy, not a mode switch.

**Note on modality:** The pipeline touches modality at three points with different concerns. (1) **Inference** (pre-generation): estimate which container type fits the task, based on complexity × autonomy × reasoning depth. This is an early, coarse decision — wrong guesses are cheap because it's reviewable. (2) **Constraint** (during task analysis): the inferred modality filters the pattern library and caps information density. A contextual modality physically cannot host a 10-panel dashboard, so there's no point generating one. (3) **Binding** (at rendering time): the abstract spec is modality-agnostic; the binding step compiles it to a container-specific layout. This separation is what makes [[fluid-modality-transitions]] possible — when the user's task complexity evolves (exploration → creation → monitoring), the system rebinds to a different container without regenerating the spec. State survives the transition. The [[adaptive-autonomy]] inversion applies: complex modalities (canvas, split-screen) default to *more user control*, not less — the modality encodes a collaboration contract, not just a viewport size.

**Current practical step:** json-render (JSON → rendered React components). This covers the `UI specification → Rendered UI` segment of the pipeline.

json-render's architecture reveals critical constraints:
- [[specification-based rendering]] is the foundation — UI as validated JSON specs, not code
- [[component catalog as schema]] establishes the boundary between AI and implementation — the catalog defines what's generatable
- [[guardrailed generative UI]] shows how to make AI generation production-ready through three layers: schema validation (Zod), component whitelisting (catalog registry), and action constraints (predefined behaviours)
- [[streaming specification compilation]] enables progressive rendering, improving perceived latency

Everything upstream must respect these constraints — task analysis must produce specs matching catalog schemas, mapping rules must target components that exist in the catalog.

**Upstream transformation pipeline** (informed by model-based UI — a different lens on the same generation pass, showing MBUI abstraction layers rather than user-facing checkpoints):

```
User prompt
  → Task model (what the user wants to do)
    → Dialog model (sequences + navigation)
      → Presentation model (abstract UI elements)
        → Layout model (concrete positioning)
          → json-render spec (type/props/children)
            → Rendered UI
```

Each arrow is a [[pattern-driven transformation]]. The LLM:
1. Analyses user prompt → identifies task patterns (Search, Login, Multi-Value Input, etc.)
2. Instantiates task patterns with context-specific parameters
3. Transforms task patterns → dialog patterns (Wizard, Recursive Activation)
4. Transforms dialog patterns → presentation patterns (Form, Unambiguous Format)
5. Transforms presentation patterns → layout patterns (Portal, House Style)
6. Compiles layout patterns → json-render specs targeting catalog components

**Shortcut possibility:** Collapse intermediate layers. Go directly from Task → json-render spec, with Dialog/Presentation/Layout as implicit transformation steps the LLM internalises. Faster but less inspectable. Trade-off between speed and transparency.

**Pattern library structure** (maps to atomic design methodology):
- **Atomic patterns** = single catalog components (Button, Input, List) — design system primitives
- **Molecular patterns** = compositions of atomic patterns (Form = Input fields + Submit button) — design system compound components
- **Organism patterns** = complete UI sections (Search = Form + Results + Filters) — design system templates/examples

LLM operates primarily at organism level, composition handles the rest.

**Design system integration:** Instead of building from scratch, use an existing design system:
- Component catalog = design system's component library (e.g., Radix primitives, MUI components)
- Pattern library = extracted from design system documentation and examples
- Design tokens = abstraction layer for theming/customisation
- Semantic components (PrimaryAction, DangerButton) help LLM pattern matching

### Open design questions

1. **What should the intermediate representation look like?** ✓ Partially answered: [[model hierarchy]] suggests Task → Dialog → Presentation → Layout as intermediate layers. Each is a distinct artefact. Open question: do we generate and store all four, or just Task + final spec with intermediate layers as ephemeral transformations? **Industry convergence (2025–26):** Three specs now compete — Google's A2UI (flat adjacency list + separate data model + JSON pointer bindings), OpenAI-aligned Open-JSON-UI (token-efficient, needs smart client interpretation), and json-render (nested `{type, props, children}`). All declarative JSON, no code. A2UI's key architectural choice: *separating the component tree from the data model* (components bind to data via paths rather than embedding values in props). This directly enables two-way binding and incremental updates — the component tree doesn't change when data changes. Trade-off identified: "easy generation or easy rendering, not both" — A2UI is verbose but directly renderable; Open-JSON-UI is compact but needs a translation layer.

2. **How do you map data types to UI components?** ✓ Answered: [[abstraction-to-concrete mapping]] via two complementary mechanisms. [[constraint-driven component selection]] handles leaf-level mapping deterministically (cardinalities/types → components). Pattern libraries handle structural mapping (task patterns → UI section patterns). Default mappings (String → TextInput, Boolean → Checkbox, `only` → Dropdown) should be baked into the system as rules; LLM only needed for ambiguous cases. Mappings must target catalog components only.

3. **How does the model evolve?** When a user changes a requirement, what changes in the data model and how does that propagate to the UI? Cambria's "lenses" approach (live bidirectional schema translation) is one answer. json-render reveals a constraint: updated specs must remain catalog-valid. New constraint from patterns: variable changes should cascade through [[pattern composition]] hierarchies. **Varv adds a third strategy**: [[accretive-extensibility]] — modifications are new definition layers, not edits to existing definitions. The runtime merges base + overlays. This makes evolution safe (base is untouched) and reversible (remove overlay to revert). The question becomes: can user modifications be expressed as overlay concept definitions, and can overlays survive base regeneration?

4. **Where does the LLM sit?** ✓ Clarified: LLM is a **pattern instantiation engine**. It selects patterns, binds variables, composes them, transforms them through layers. Generates specs (validated JSON), never code. Operates within constraint grammar defined by pattern library + catalog. LAUI adds: LLM may also sit *alongside* as persistent operator ([[LLM-operable interface]]).

5. **One-way vs. two-way rendering?** json-render is currently one-way (spec → UI). DFRP is two-way (UI ↔ JSON). What does it take to close the loop? User edits in UI need to flow back to spec, potentially back through pattern instances to task model. [[UI derivation process]] currently assumes top-down; needs to work bottom-up too. **A2UI's answer:** separate the data model from the component tree. Components bind to data via JSON pointer paths (`BoundValue`). User edits update the data model; the component tree stays stable; bindings reactively reflect new values. AG-UI's protocol adds event-sourced state diffs (STATE_SNAPSHOT + STATE_DELTA using RFC 6902 JSON Patch) for efficient incremental sync between agent and UI. This is essentially DFRP implemented as a protocol.

6. **Catalog design**: How wide should guardrails be? Too narrow = users hit walls. Too wide = safety erodes. Can catalogs be extended dynamically, or are they build-time fixed? LAUI suggests the catalog also needs semantic metadata per entry so an agent can make informed selections ([[LLM-operable interface]]). New: catalog entries should map to patterns they implement for reverse lookup. **A2UI formalises catalog negotiation**: server advertises supported `catalogId`s, client declares `supportedCatalogIds`, both agree before rendering. Standard catalog covers: Layout (Row, Column), Display (Text, Image, Icon, Divider), Interactive (Button, TextField, CheckBox), Container (Card, Modal, Tabs, List). This is roughly the same granularity as json-render's catalog — practical validation that this component level is right.

7. **Pattern library size**: The model-based UI paper documents dozens of patterns. Too many for manual selection, but potentially tractable for LLM. How do you build a library that's comprehensive yet learnable? What's the right granularity?

8. **Transformation reliability**: [[Pattern-driven transformation]] codifies mappings, but how do you validate them? Can you test that a task pattern reliably produces sensible presentation patterns? What's the error handling when transformations fail?

9. **Pattern customisation**: Can users edit patterns themselves post-generation? Modify variable bindings? Swap sub-patterns? How much of the [[pattern composition]] structure should be exposed?

10. **User context integration**: How does [[context-driven adaptation]] feed into the pipeline? As prompt context for the LLM? As post-processing rules on the spec? As adaptation directives from a separate reasoning engine? OADAPT argues for a separate semantic layer; simpler approaches include CSS `prefers-*` queries and responsive design. Accessibility adaptations probably need deterministic rules; preference adaptations can be LLM-contextual.

## Key tensions

- **Isolation vs. coordination in UI composition**: components need isolation to be reasoned about locally, but coordination to create rich UX. PushPin went too far towards isolation; Embark showed the power of deep context sharing. Pattern libraries must encode both structural composition (how patterns nest) and runtime coordination (how resulting components communicate).
- **AI-generated apps vs. assembled tools**: generating a complete interface from a prompt produces an "app" (monolithic, sealed). The malleable software vision wants composable tools. Can these be reconciled?
- **One-shot generation vs. continuous operation**: ~~the pipeline currently assumes generate-once-then-render~~ (this framing is outdated — DuetUI's [[bidirectional-context-loop]], AG-UI's event streams, and the architecture sketch's feedback loop all assume continuous operation). The tension now is more specific: *within a session*, the system continuously refines (validated by DuetUI, N=24). But *across sessions*, does the system start fresh or resume? [[intent-specification-as-common-ground]] suggests persistent intent specs carry forward, but the generated UI itself may not survive between sessions. The deeper version: how much state is ephemeral (per-session) vs. durable (cross-session)?
- **Malleability implementation**: The [[gentle slope]] can be concretely designed using [[model hierarchy]] as intervention points: View → Tweak values → Customise attributes → Swap patterns → Edit specs → Edit models. Each step requires incrementally more knowledge. [[fluid-attributes]] (from Min et al., 2025) fills a critical gap: between value editing and pattern manipulation, users can add/remove/reformat data attributes using their own vocabulary. Without this step, users face a cliff from "viewing" to "editing JSON".
- **Ontology richness vs. generation speed**: Formal ontologies ([[ontology-driven UI generation]]) produce the most reliable UIs because constraints are explicit and mapping is deterministic. But they're expensive to create (requires domain expertise, ontology engineering). Lightweight schemas are fast to generate (LLM can produce them from a prompt) but lack the constraint richness that enables [[constraint-driven component selection]].
- **UI-only specs vs. full application specs**: The pipeline currently targets json-render specs (UI structure only). Varv argues the output should be richer: [[software-as-data-structure]] that includes behaviour (actions, triggers) and data mappings, not just layout. Richer specs enable better tooling (inspectors, editors) and better composition ([[accretive-extensibility]]). But they're harder to generate, harder to validate, and harder for users to understand. The pragmatic minimum might be: UI spec + state schema + action rules — enough for two-way binding and basic interactivity, without Varv's full event-flow model.
- **Regeneration vs. accretive modification**: When a user changes intent, should the system regenerate from scratch ([[pattern-driven transformation]] through all layers) or layer a modification on top ([[accretive-extensibility]])? Regeneration is simpler but destroys user customisations. Accretive modification preserves customisations but can produce inconsistent states if the modification conflicts with the base. A2UI's data/component separation and Varv's accretive layering suggest a hybrid: regenerate the base spec, re-apply compatible overlays. Meridian validates this in practice: base config + user overlay config, merged at runtime.
- **Component-centric vs. attribute-centric specs**: json-render specs are component-centric (`{type, props, children}`). Meridian specs are attribute-centric (`{data, attributes, views, layout}`). The component-centric approach is closer to rendering; the attribute-centric approach is closer to user mental models. For information-seeking tasks (browse, compare, select), attributes are the natural unit. For creation tasks (forms, editors), components may still be primary. The pipeline may need both: attribute-centric specs for content customisation, compiled down to component-centric specs for rendering.
- **Structural composition vs. behavioural specification**: Most UIs can be assembled from patterns + components without named behavioural concepts. But some — authentication, scoring, approval workflows, real-time collaboration — have state transitions and side effects that structural composition can't express cleanly. The tension: adding concept infrastructure too early creates overhead and [[concept-entropy]] (Palantir's warning); adding it too late means retrofitting behavioural specs into an architecture that wasn't designed for them. The hospitable-architecture approach (clean layer separation with an empty rule layer) hedges both ways, but "empty layer that might be used later" has a history of becoming dead code. The test: can the first few generated UIs that hit the behavioural wall be retrofitted without pain? If yes, the bottom-up approach works. If not, some upfront concept infrastructure was warranted after all.
- **Shared state vs. explicit bindings for composition**: Varv/JELLY share all state through a centralised model — easy to build, hard to reason about, easy for an LLM to generate (one schema). Déjà Vu shares nothing except IDs — harder to build, easy to reason about, harder for an LLM to generate (needs a binding template on top of concept schemas). For the pipeline: shared state is the pragmatic starting point (JELLY already validates it), but the binding template idea is worth keeping in reserve for when cross-component coordination gets complex.
- **Design-time vs. data-time LLM use**: [[ai-attribute-reformulation]] reveals that the LLM has two distinct roles with different timing. Spec generation happens once at design time; attribute reformulation happens per data item at fetch time. These have different latency requirements, different cost profiles, and different failure modes. Reformulation errors corrupt data display (factual harm); spec generation errors produce bad UI (usability harm). Different reliability bars.
- **Transparent mediation vs. generation speed**: Park et al.'s [[semantic-intermediate-layer]] significantly improves user control and satisfaction, but adds a step (semantic review/correction) to the generation loop. The user study showed unanimous benefits, but for simple, well-understood UIs, the overhead of reviewing 15 semantic slots may not be worth it. The tension: maximum transparency (every semantic decision visible and editable) vs. maximum flow (prompt → UI with minimal interruption). [[hierarchical-design-semantics]] supports partial specification (leave slots empty for AI inference), which suggests a progressive approach — show only high-confidence parsed semantics by default, expand to full framework on demand. But this reintroduces the evaluation problem for unspecified slots.
- **Iteration by scoped editing vs. iteration by regeneration**: Park et al.'s [[scoped-semantic-editing]] (semantic diffs + code anchor) prevents [[semantic-drift]] but constrains the AI to incremental modifications of existing code. For major intent changes ("actually, make this a dashboard instead of a form"), scoped editing is insufficient — you need full regeneration. The question is where the boundary falls, and whether the system can detect when a scoped edit would produce worse results than starting fresh. [[accretive-extensibility]] (Varv/Meridian) is a third option: regenerate the base but preserve user overlays.
- **Intent specification depth vs. user patience**: IntentFlow's [[intent-decomposition]] extracts 5–10 dimensions per writing task. A multi-entity UI task (e.g. "plan a dinner party") could have dozens of dimensions across multiple intents. Users benefit from seeing and adjusting these dimensions (user study showed significant improvements in control and satisfaction), but there's a point where the specification overhead exceeds the value. Progressive disclosure (show top dimensions, expand on demand) is the obvious solution, but how to rank dimension importance is unresolved. The design-level semantic framework (Park et al.) has the same problem — 15 slots is already a lot. Two specification layers (intent dimensions + semantic slots) compounds it.
- **Implicit intent quality vs. user trust**: IntentFlow's implicit intent extraction scored 4.17/5 for completeness — good but not exhaustive. Missing implicit intents surface as disappointment in the output ("why didn't it consider X?"). Wrong implicit intents surface as wasted adjustment effort ("I don't care about formality, why is there a slider for it?"). For the genUI pipeline, where implicit intents drive pattern selection and spec generation, the cost of getting them wrong is higher than in text generation — a wrong UI structure is harder to fix than a wrong paragraph.
- **Conversational vs. instrumental interaction**: Chat (IntentFlow, Park et al.) treats AI interaction as a dialogue — structured, sequential, turn-based. Instruments (AI-instruments) treat it as direct manipulation — spatial, concurrent, persistent. Chat is easier to implement (text in, text out) and easier for users to start with (everyone knows how to type). Instruments are more expressive (spatial scoping, multi-dimensional adjustment, non-linear exploration) but require learning new interaction paradigms. For the pipeline: the first version will inevitably be chat-based, but the architecture should not assume chat as the only input modality. Intent objects, spatial scope, and grounding-by-example should be possible future additions without architectural upheaval.
- **System-driven vs. user-driven intent structuring**: IntentFlow and NeuroSync structure intent *for* the user (system decomposes, user reviews). Intent tags let the user structure intent *themselves* (user authors tags, system suggests). The system-driven approach is faster to start but risks wrong decompositions. The user-driven approach gives more control but requires the user to know what dimensions matter. IntentTagger's hybrid (ground from text prompt → user edits) suggests the answer isn't either/or — start system-driven, then hand control to the user as they gain understanding. But the two approaches may need different pipeline architectures (decomposition engine vs. tag suggestion engine).
- **Intent discovery vs. intent overload**: [[meta-intent-elicitation]] demonstrably helps users discover what they want, but too many suggestions overwhelm ("maybe less overloaded with suggestions" — P01). The system needs to expand the user's awareness of the decision space without flooding it. The opposite slider was used for reflection not steering — suggesting that *thinking tools* and *specification tools* may need separate design considerations.
- **Prospective vs. retrospective alignment**: The pipeline has accumulated many pre-generation checkpoints: intent decomposition (IntentFlow), task graph (NeuroSync), semantic layer (Park et al.). Each adds alignment quality but also interaction cost. Terry et al.'s [[alignment-cost-tradeoff]] makes the counterargument: for low-stakes, reversible decisions, acting first and offering retrospective refinement (CoPilot-style accept/dismiss) is cheaper than full upfront specification. The pipeline needs to distinguish high-stakes decisions (task model structure, entity relationships — worth a prospective checkpoint) from low-stakes ones (layout preferences, colour scheme — handle retrospectively via in-place editing). This connects to [[adaptive-autonomy]]: the checkpoint density should adapt to the user's current cooperation phase, not be fixed. **Strengthened by oversight findings**: the temporal transparency principle (Grunde-McLaughlin et al.) provides direct evidence — process-oriented transparency works prospectively (for steering), outcome-oriented transparency works retrospectively (for verification). Pre-generation checkpoints should show the decision process; post-generation review should decompose outputs into Requirements vs. Assumptions. Using the wrong transparency type at the wrong time actively harms performance ([[process-induced-overreliance]]). [[uncertainty-driven-elicitation]] (InterQuest) offers a principled mechanism for deciding *which* prospective checkpoints to surface: compute entropy across the system's knowledge, surface checkpoints where uncertainty is highest.
- **Patterns-as-templates vs. generating systems**: The pipeline currently treats patterns as static building blocks — select, parameterise, compose, render. But Alexander himself moved away from this interpretation. His later work (*The Nature of Order*, 2002–04; OOPSLA '96 keynote) argues patterns are insufficient without a *generative process*: structure-preserving transformations that iteratively strengthen the whole by identifying and addressing the weakest centre. The pipeline's feedback loop (`↺ customisation → model evolution → UI update`) is structurally closer to Alexander's generating systems than to his pattern languages, but the vault lacks the vocabulary to describe it that way. The "pattern instantiation engine" framing may be selling the pipeline short — or misdirecting the architecture toward batch-style generation when the real mechanism is incremental, context-sensitive transformation. Needs further reading: *The Nature of Order*, *The Nature of Software* series, Alexander (1968) "Systems Generating Systems."
- **Translation vs. creation**: The pipeline translates user intent into existing component patterns (horizontal formalisation). It doesn't support users or the system inventing genuinely new representational forms (vertical creation). Zhang et al. (2025) argue LLMs actively impede notation evolution by amplifying established patterns and starving novel ones. For the pipeline: user modifications that break existing patterns (replacing a table with an ad-hoc spatial layout, combining components in unintended ways) should be treated as potential notation invention, not errors. The [[configuration-model-as-design-space]] helps surface gaps (no valid point for the user's need), but filling those gaps requires capability the pipeline doesn't have yet. Long-term aspiration, not a near-term fix.
- **Schema-free vs. schema-bound specification**: Intent tags are schema-free (users define whatever [label: value] pairs they want). Park et al.'s semantic hierarchy is schema-bound (15 named slots in 4 levels). Schema-free is more flexible and tolerant of ambiguity ([[graduated-ambiguity-tolerance]]) but produces less predictable input for downstream generation. Schema-bound enables reliable pattern matching but forces users into a predefined vocabulary. Users in the IntentTagger study wanted to customise even the minimal grouping structure (Narrative, Visual Style, Content Sources). For the pipeline: the intent layer should probably be schema-free (accept anything), but the semantic layer should be schema-bound (map to a defined structure for pattern selection).
- **Ephemeral prompt vs. persistent intent specification**: The pipeline was designed around per-session prompts — the user types something, the system generates. SemanticCommit introduces a second input channel: a persistent [[intent-specification-as-common-ground]] document that accumulates preferences across sessions. The tension: ephemeral prompts are flexible (each session starts fresh, no legacy constraints) but lose learning (the system forgets what the user likes). Persistent specs carry forward preferences but accumulate cruft and require maintenance (conflict detection, impact analysis). For the pipeline: the per-session prompt and the persistent spec need to be *composed*, not just concatenated. When they conflict ("persistent spec says formal tables; today's prompt says casual cards"), which wins? The prompt, presumably — but the conflict should be surfaced, and resolving it may update the spec.
- **Structured taxonomy vs. fluid scope for user preferences**: OADAPT models user context through structured ontological taxonomies — hierarchical categories with formal relationships. This works well for accessibility needs (disability types *are* taxonomically structured). But InterQuest's [[cross-task-user-knowledge]] finding reveals that *preference* boundaries are fluid and overlapping, not tree-structured. A user might prefer "dense tables" for financial data but "spacious cards" for content browsing — the scope is contextual, not categorical. For the pipeline: the user profile needs two sub-models with different structures. Accessibility needs → structured taxonomy (OADAPT-style, deterministic rules). Interaction preferences → knowledge items with fluid scope + confidence (InterQuest-style, entropy-driven refinement).
- **Interaction quality vs. interaction quantity**: [[interaction-as-intelligence]] argues that the combined system's intelligence is a function of interaction quality, not just model capability. But [[dynamic-cooperation-willingness]] shows users don't *want* constant interaction — they oscillate between hands-on (clarification, intervention) and hands-off (reasoning, summarisation) phases. The pipeline's intermediate checkpoints should match this rhythm: demand attention at clarification and review stages, offer transparency-without-interruption during transformation and reformulation stages. The risk: designing checkpoints around the *average* user's cooperation pattern when individuals vary. [[usage-as-annotation]] offers a resolution: detect the user's current cooperation phase from behavioural signals and adapt checkpoint intensity accordingly.

## Gap map

Upstream (not yet covered by json-render):
- ✓ **Task analysis → data model**: [[Pattern-driven transformation]] provides the mechanism. LLM identifies task patterns, instantiates them with context parameters. Remaining gap: building the actual pattern library.
- ✓ **Data model → UI spec**: [[Abstraction-to-concrete mapping]] via patterns that transform through [[model hierarchy]]. Task patterns → dialog patterns → presentation patterns → layout patterns → json-render specs. Remaining gap: implementing the transformation pipeline.
- **Alexander's later work (generating systems, living structure)**: The vault's treatment of patterns draws entirely from the software pattern tradition (Gang of Four → Seffah & Gaffar → design systems), which Alexander himself critiqued as taking the wrong thing from his work. His *Nature of Order* (2002–04) proposes structure-preserving transformations and fifteen properties of living structure as the actual generative mechanism — iterative, use-time, context-sensitive, not design-time template selection. This may reframe the pipeline's evolution loop and the LLM's role within it. Planned reading: *The Nature of Software* series (translates *Nature of Order* into software terms), possibly *The Nature of Order* itself. Until then, the "pattern instantiation engine" framing should be understood as provisional — it captures the batch generation step but may not be the right model for the continuous evolution step.
- **Pattern library construction**: What patterns to include? At what granularity? How to validate pattern mappings work reliably? How to make patterns LLM-selectable (semantic metadata)? **Possible answer:** Extract from design system documentation rather than building from scratch — see [[design systems as pattern libraries]].
- **Catalog-pattern alignment**: Ensuring presentation/layout patterns only reference catalog components. Build-time validation needed.
- **Constraint rule library**: Building the default mapping table for [[constraint-driven component selection]] — which data shapes and cardinalities map to which catalog components. Should be straightforward for common types (string, number, boolean, enum, date, arrays) but needs extension points for domain-specific types.
- **Configuration space representation**: Kumbang's [[configuration-model-as-design-space]] suggests the pipeline output should encode variation points (what can vary) and constraints (what combinations are valid), not just a single spec. Open question: what's the lightweight version of this for json-render-compatible output? JSON Schema's `oneOf`/`anyOf`/`enum` encode some variation, but cross-cutting constraints (if feature X, then component Y must exist) need something richer. Could the spec include a `variationPoints` section alongside the component tree?
- **Feature-component bridging rules**: [[feature-component-duality]] says features and components need formal links. For the pipeline: when the user says "remove the calendar view" (a feature-level change), which components should be removed or modified? Currently this is implicit in the LLM's understanding. Making it explicit (as Kumbang does with implementation constraints) would enable deterministic propagation of feature changes to component specs.
- **Schema enrichment**: How much constraint metadata should the LLM include when generating data schemas from user prompts? Bare types are insufficient for constraint-driven component selection. At minimum: cardinality (optional/required/one/many), enum values, length hints. Ideally: semantic relationships between entities.
- **Objective induction as pipeline entry point**: [[just-in-time-objective-induction]] (Lam et al., CHI '26) shows the per-session prompt can be *derived from* context observation rather than stated. The pipeline's pre-generation phase could start before the user prompts: observe workspace context → induce objectives → present for review → feed into intent decomposition. Open questions: how to compose induced objectives with the persistent intent spec (when they conflict, which wins?), how rich the context observation needs to be (Poppins uses a single screenshot; a generative UI system with an existing data model and interaction history could use much more), and whether induced objectives should be hierarchical (connecting to [[intent-decomposition]]) or flat (as Poppins implements them). The 97.8% selection rate for system-generated objectives over custom ones suggests anchoring bias — induced objectives should be clearly presented as suggestions, not facts.
- **Generate-then-rank as pipeline-wide pattern**: [[generate-then-rank-with-objectives]] (Lam et al.) is implemented as simple prompt prepend for generation + JSON spec addition for evaluation, but the pattern could apply at every pipeline stage that has both generation and evaluation: task analysis, pattern selection, spec generation, attribute reformulation. Open question: one top-level objective steering the whole pipeline, or per-stage objectives derived from the top-level one?
- **Context awareness** and personalisation — how do user history/preferences inform pattern selection? LAUI's answer: an agent that studies the user at use-time ([[emergent workflow]]). OADAPT's answer: a structured user profile model + adaptation rules ([[context-driven adaptation]]). These are complementary: rules handle known adaptations deterministically, agent handles novel ones.
- **User profile schema**: What user context fields matter for UI generation? At minimum: accessibility needs, experience level, preferences (theme, density, language). OADAPT's User Profile Ontology provides a comprehensive taxonomy but is overkill for most cases. A simpler JSON schema covering the key dimensions would suffice. ✓ **Partially answered by OADAPT specification**: The UPO provides a concrete taxonomy (measurable: age, education, experience; nominal: gender, language, disability with subtypes). The 30 adaptation rules provide a reference implementation mapping user traits → UI modes. These can be extracted into a lightweight JSON schema + rule table without the OWL formalism.
- **Adaptation rule library**: The OADAPT specification provides 30 WCAG-derived rules (disability → UI mode) plus 3 mutual exclusion constraints. Jerry et al. (2025) add 42 Derived Accessibility Requirements (DARs) with formal normative traceability and a concrete implementation pipeline. The [[content-structure-adaptation-split]] clarifies *how* these rules should be implemented: structural rules as deterministic post-processing, content rules as LLM prompts with [[adaptation-quality-gates]]. Stefanidi et al. (2022) add a third mechanism for *when adaptations interact*: [[optimisation-based-ui-adaptation]] handles joint selection + LoD + placement through combinatorial optimisation. Remaining gap: preference-based and environment-based adaptation rules are still largely unspecified. The content quality gate mechanisms (NLI-based fidelity, readability scoring) need to be generalised beyond the healthcare domain. And the cognitive load bound ([[cognitive-load-bounded-display]]) needs empirical calibration for web UIs (Stefanidi et al. calibrated for AR HUDs).
- ✓ **Attribute configuration layer**: [[fluid-attributes]] (Meridian) provide a concrete mechanism for the layer between data model and UI spec. Attributes are defined with sources, types, formatters, and optional AI reformulation prompts. Remaining gap: how does this layer interact with pattern-driven transformation? Do patterns define attribute *slots* that the LLM fills, or does the attribute config drive pattern selection?
- **Domain-specific task model validation**: Can the [[task-model]] represent real business domain tasks at the right granularity? The experiments ([[Implicit requirements aren't surfaced]]) test this: the LLM decomposes business intent ("make product X available in channel B") into task models, grounded in domain knowledge, and executes via WebMCP against the existing app. This inverts the pipeline — instead of task model → generate UI, it's task model → drive existing UI — isolating the task decomposition question from rendering. If tasks decompose into reusable patterns, that seeds the pattern library. If domain grounding proves essential (as [[knowledge-graph-grounded-generation]] predicts), it informs what the IR ([[milestones#O2a — No intermediate representation|O2a]]) needs to include.
- **Concept catalog construction (revised scope)**: Déjà Vu's [[concept-catalog]] of 18 generic concepts covered 8/12 student projects. But per the revised position ([[concept-as-behavioural-annotation]]), the catalog is a **knowledge resource**, not a mandatory pipeline stage. The catalog should focus on **behavioural patterns that structural composition can't express** — authentication flows, scoring systems, approval workflows, real-time collaboration, state machines with complex side effects. Building it bottom-up: start empty, add concepts as generation encounters cases where patterns + components fail. Palantir's experience warns of [[concept-entropy]] at scale — active curation needed. Kodless shows the catalog has a secondary value: concept-named prompts improve LLM generation quality ([[concept-spec-as-generation-checkpoint]]), even when the output isn't concept-structured.
- **AI reformulation infrastructure**: [[ai-attribute-reformulation]] requires per-item LLM calls at data-fetch time. Needs: batching strategy, caching layer, output type validation, fallback for LLM failures, visual indicator distinguishing AI-derived from raw attributes. Also: prompt quality tooling (reformulation prompts require iteration).
- ✓ **End-user customisation mechanism**: Meridian's spec overlay model validates [[accretive-extensibility]] for attribute-level customisation. Users can add/remove/reformat/reorder attributes, and all modifications are reversible overlays. Remaining gap: does this model extend to pattern-level customisation (not just attribute-level)?

Interaction paradigm (from Xu et al.):
- ✓ **Runtime collaboration mechanism**: [[bidirectional-context-loop]] provides a concrete paradigm for how human and agent collaborate on a generated interface — agent generates, user manipulates, actions feed back as implicit context, agent updates. DuetUI validates this with N=24 (SUS 73.65 vs. 63.5 baseline, p=.002). Remaining gap: DuetUI used simulated data. Real API integration adds latency and error. How fast must the loop cycle to feel fluid? DuetUI's agents used GPT-4o + Groq for speed.
- **Action history as context accumulator**: DuetUI's bidirectional action history is a concrete implementation of context accumulation, but it grows unboundedly. For long-running tasks, context window management (summarisation, sliding windows, relevance-weighted pruning) is needed. No paper has addressed this for UI co-generation specifically.
- **Adaptive control allocation**: [[adaptive-autonomy]] is validated qualitatively (users want shifting control) but not implemented adaptively in DuetUI (it uses fixed stages). Building reliable expertise inference from interaction patterns is an open research problem. [[cognitive-engagement-for-reliance]] (Raees et al.) adds a complementary signal: autonomy should track not just expertise but *analytical engagement depth* — has the user explored, experimented, and constructed, or just prompted? The four-phase engagement model (driver analysis → what-if → model building → evaluation) could inform checkpoint density: early stages warrant more checkpoints (building scaffolding), later stages fewer (reliance is calibrated).
- ✓ **Agent capability discoverability**: [[tangible-agency]] validates that embedded controls beat conversational prompting for non-expert users (15/24 reported reduced prompting burden). Remaining gap: how to generate these controls — the component catalog needs agent-interactive components (search buttons, refinement sliders) alongside data-display components.

Downstream (json-render limitations):
- **Two-way binding**: How does json-render become bidirectional? User edits in UI → spec updates → pattern instance updates → task model updates. [[UI derivation process]] needs to work bottom-up. **Varv's approach**: concepts define actions (state transitions) alongside schemas (state shape). The view triggers actions; actions modify state; the view reactively updates. Combined with A2UI's data/component separation, this suggests: separate the data model from the component tree, let components bind to data via paths, and define valid state transitions as actions.
- **Cross-component communication**: How do independently rendered components share state? [[pattern composition]] creates hierarchies, but how do sibling patterns coordinate? **Varv's answer**: no encapsulation — all concept state is shared via a centralised store. Any concept can reference any other concept's properties. This enables cross-cutting features but makes reasoning harder. Trade-off between PushPin's isolation (safe but limited) and Varv's openness (powerful but fragile).
- **Data integration**: Connecting generated UIs to external data sources (JELLY explicitly scopes this out)
- **Spec evolution**: When user intent changes, how do specs update? Full re-derivation through all layers? Incremental pattern variable updates? Localised regeneration? **Varv adds an option**: [[accretive-extensibility]] — layer modifications on top of the base spec. The base can be regenerated independently; user customisations survive as overlay layers (assuming stable concept names as identifiers).
- **Behaviour specification**: Should the pipeline's output include interactive behaviour (state transitions, event handling), not just UI structure? Varv says yes — [[software-as-data-structure]] encodes the full application. The pragmatic question: how much behaviour can an LLM reliably generate? UI layout generation is already challenging; correct state machine generation is significantly harder.

Transformation mechanics:
- **Validation checkpoints**: At each transformation layer, how do you validate output quality before proceeding?
- **Error recovery**: When transformation fails (pattern doesn't fit, invalid parameters), backtrack to previous layer or restart?
- **Ambiguity resolution**: Multiple valid transformation paths — how to choose between them? AmbigChat (Ma et al., UIST '25) shows one approach for QA: build a disambiguation tree from a facet taxonomy and let the user navigate it via interactive widgets. The tree pattern (hierarchical facets, breadth-first expansion, user-driven pruning) could generalise to pipeline transformation choices — surface branching points as interactive checkpoints rather than resolving them silently.

Task understanding externalisation (from Zhang et al.):
- **Three-layer transparency**: The pipeline now has three candidate intermediate layers for user inspection — intent decomposition (what the user wants), task understanding graph (what the LLM plans to build), and semantic specification (how it should look). Open question: should all three be separate panels/steps, or can they be collapsed? NeuroSync's intent tree + understanding graph + mapping is one approach. Could the semantic layer absorb the task graph (e.g., semantic slots include functional decomposition)? **Partially answered by temporal transparency principle** (Grunde-McLaughlin et al.): all three layers are appropriate as *pre-generation steering* tools but risk [[process-induced-overreliance]] if surfaced as *post-generation verification*. The design question is less "how many layers?" and more "which layers appear at which pipeline phase?" Pre-generation: show all three for steering. Post-generation: switch to [[outcome-oriented-verification]] (Requirements/Assumptions decomposition) instead.
- **Distillation for pipeline efficiency**: NeuroSync's SLM distillation (fine-tune a small model to extract structured representations in a single pass instead of multiple LLM calls) is a general technique applicable to any pipeline stage where extraction latency matters. Could apply to: intent decomposition, semantic parsing, augmented semantics extraction. Remaining gap: need training data generation strategy for each stage.
- **Intent-aware simplification for pipeline views**: [[intent-aware-simplification]] could apply to any user-facing representation, not just task graphs. The spec tree, the semantic layer, even the component catalog could be intent-filtered. Remaining gap: how to track "current intent" in a multi-step UI generation workflow where the user's focus shifts between functional areas.

Intent communication (from Kim et al. + Henry Riche et al.):
- ✓ **Intent structuring mechanism**: [[intent-decomposition]] provides a concrete three-level hierarchy (Goal → Intents → Dimensions) for decomposing user prompts before design-level specification. Remaining gap: validated for single-output writing tasks only. Multi-entity, multi-view UI tasks need validation — does the decomposition scale, and do dimensions need nesting?
- **Intent-design integration**: How do intent dimensions feed into [[hierarchical-design-semantics]]? The Goal level maps roughly to Product; Intents map to Features. But the mapping isn't mechanical — a "collaboration: solo ↔ team" intent dimension affects Product.Target User, Feature.Function, AND Component choices simultaneously. How to cascade intent dimensions through the design semantic framework is an open design question.
- **Intent persistence**: Can [[intent-decomposition]] produce reusable intent profiles? If a user always wants "detailed complexity" and "rich visualisation," those dimensions could become part of a persistent user preference model ([[context-driven adaptation]]) rather than being re-extracted each time. This bridges IntentFlow's per-session dimensions with OADAPT's persistent user profiles. **Partially addressed by** [[cross-task-user-knowledge]] (InterQuest) — persistent preferences are not intent *dimensions* but structured knowledge items with content + scope + confidence. InterQuest shows this works for information-seeking (87.50% accuracy). **Further addressed by** [[intent-specification-as-common-ground]] (SemanticCommit) — intent specifications (CLAUDE.md, cursor rules) are the concrete, human-readable *storage mechanism* for persistent user intent. SemanticCommit tackles the integration problem: how to commit new preferences without breaking existing ones. KG-based conflict detection handles the merge. Remaining gap: the bridge from UI generation to intent specification updates — when a user modifies a generated UI, how does that implicit preference change get surfaced as a candidate "commit" to their intent specification?
- **Traceability reliability**: [[intent-output-traceability]] depends on LLM-computed links between dimensions and output elements. For the genUI pipeline, where output is a multi-component UI (not text), the linking surface is much larger. Can traceability be partially deterministic (constraint rules → components are fully traceable) with LLM linking only for ambiguous/creative decisions?

Instrumental interaction (new from Henry Riche et al.):
- **Prompt reification for UI generation**: AI-instruments were prototyped for image generation. Transferring [[prompt-as-interface-object]] to structured UI generation raises questions. Spatial scoping (Lenses) maps to pixel regions — for UI, scope should be *component hierarchy* or *semantic region* rather than drawn rectangles. Grounding-by-example (Brushes) extracts visual style from images — for UI, what attributes can be extracted from an example interface? Design tokens are easy; interaction patterns harder; data model structure hardest.
- **Input modality architecture**: The pipeline currently assumes text input. AI-instruments argue for multiple input modalities: text prompts, reified intent objects (Fragments), spatial scoping (Lenses), and example grounding (Brushes). How should the pipeline accept and unify these? One approach: all modalities produce the same intermediate representation (intent decomposition), which then feeds the pipeline uniformly. The modality is just a different front door to the same structured intent.
- **Instrument composition for UI customisation**: Meta-instruments (instruments taking other instruments as input) could map to the pipeline as "modification instruments" — a Lens-like tool that takes a pattern as input and applies it to a selected component subtree. Or a Fragment-style tool that decomposes an existing generated spec into editable attribute cards. How to design composable modification instruments for generated UIs is unexplored.

Semantic bridging (new from Park et al.):
- ✓ **User-facing specification structure**: [[hierarchical-design-semantics]] provides a concrete framework for what users need to specify. Remaining gap: how does this interact with [[pattern-driven transformation]]? Should semantic slots drive pattern selection, or do patterns define which slots are relevant?
- ✓ **Preventing iteration degradation**: [[scoped-semantic-editing]] via semantic diffs prevents [[semantic-drift]]. Remaining gap: this was validated for single-component generation only. Multi-component systems need scope boundaries that cross component boundaries (when should editing one component's semantics affect siblings?).
- **Semantic extraction reliability**: [[augmented-semantics]] depend on LLM analysis of generated code + screenshot. How reliable is this extraction? Can it be partially deterministic (component-level properties from code, higher-level semantics from LLM)?
- **Semantic-pattern integration**: The pipeline has two structured layers that need to connect — the user-facing semantic framework (Product → Design System → Feature → Component) and the generation-facing pattern library (task patterns → dialog patterns → presentation patterns). How do semantic slot values map to pattern selection and instantiation?

Modality selection (from Andru & Saksena):
- ✓ **Modality as top-level pattern choice**: Now addressed in the architecture sketch. Modality inference runs after intent decomposition (using task complexity × autonomy × reasoning depth), is reviewable by the user, and constrains pattern selection downstream. Remaining gap: the inference heuristic itself — what thresholds map complexity/autonomy/reasoning scores to specific container types? The paper provides qualitative descriptions, not decision rules. Also: the eight modality types may need collapsing for a first implementation (prompt bar, contextual, split-screen, and full-screen cover most use cases; rail, canvas, hub, and immersive can wait).
- ✓ **Modality-agnostic specs**: Now addressed in the architecture sketch. The UI specification is labelled "modality-agnostic abstract spec"; the modality binding step at generation time compiles to a container-specific layout. [[fluid-modality-transitions]] are supported via rebinding in the post-generation loop. Remaining gap: what exactly does the abstract spec look like such that it's genuinely renderable across containers? A flat attribute list (Meridian-style) adapts more easily than a deeply nested component tree (json-render-style). The abstract spec may need to be closer to Meridian's data → attributes → views → layout than to json-render's type/props/children.
- **Information density as modality constraint**: The non-linear relationship between AI reasoning and modality preference (from the evaluation) adds a constraint to the adaptation layer: AI explanations should be modality-aware. A contextual tooltip needs a one-line summary; the same reasoning in a full-screen view can have stepwise detail. This connects [[cognitive-load-bounded-display]] to [[modality-as-task-container]] — the cognitive bound varies by modality, not just by user state. The architecture sketch now includes cognitive load bounds in the modality binding step, but the specific bounds per modality type (contextual ≤5, full-screen ≤9) are placeholder heuristics needing empirical calibration for web UIs.

Monitoring and instrumentation:
- **Parallel state display**: [[parallel-state-display]] (Viégas & Wattenberg) argues the pipeline's intermediate representations should feed a persistent user-facing monitoring layer. Which intermediates are worth surfacing? Task classification, user model assumptions, and confidence scores are candidates. How to visualise instability (e.g., the system's task classification flickering between "search" and "browse") is an open design question. **Caveat from oversight findings**: persistent process visibility carries the [[process-induced-overreliance]] risk — a dashboard showing "everything looks normal" may suppress critical evaluation of the generated output. The monitoring layer should emphasise *anomalies and assumptions* (outcome-oriented) rather than *steps and progress* (process-oriented). Confidence scores and user model assumptions are safer to surface than transformation step traces.
- **Inferred user model extraction**: How to reliably extract the [[inferred-user-model]] from a hosted LLM. Structured prompting ("list your assumptions about the user") is pragmatic but may produce confabulation rather than genuine internal state. For the pipeline, the simplest approach: include a "user assumptions" extraction in the same LLM call that does task analysis, then surface it for correction. **Partially addressed by** [[cross-task-user-knowledge]] (InterQuest) — instead of extracting the model from LLM internals, *build* a separate user knowledge base from interaction data. The knowledge items (content + scope + confidence) are constructed by the LLM but stored externally, making them inspectable and correctable. [[uncertainty-driven-elicitation]] provides the refinement loop: entropy-based questioning resolves the highest-impact uncertainties in the knowledge base. This sidesteps the confabulation problem — the knowledge base is evidence-grounded and user-validated, not extracted from opaque internal state.
- **Declared vs. inferred user context reconciliation**: [[context-driven adaptation]] uses declared profiles; [[inferred-user-model]] captures runtime beliefs. When these conflict ("declared: expert; inferred: novice"), which takes priority? Probably declared, but the conflict is itself useful to surface.
- **Usage-as-annotation infrastructure**: [[usage-as-annotation]] (Ye et al.) provides a mechanism for the model evolution loop (↺) that doesn't require explicit feedback. The system needs to: (a) capture user interaction events at a useful granularity (column resizes, field reorderings, filter selections, not raw mouse movements), (b) aggregate these into preference signals (this user prefers tables over cards, wants more space for text, always removes the rating column), (c) feed signals back into the next generation or adaptation cycle. Deep Cognition's preference agent does this via in-context reinforcement learning over three dimensions (query, source, output preferences). For the pipeline, the equivalent dimensions might be: layout preferences, attribute preferences, and interaction pattern preferences. Open question: how much interaction data is needed before signals become reliable? Single-session vs. cross-session learning have very different architectural implications.

Process alignment (from Terry et al.):
- **Surrogate process for pattern selection**: The pipeline's most opaque step is the LLM choosing patterns and components. The user sees input (prompt) and output (rendered UI) but not the decisions in between. A [[surrogate-process]] for this step — a simplified representation showing "I chose Search pattern because your task involves filtering entities; I used Table for the results because you have 5+ comparable items" — would bridge the Process Gulf. Open question: should this be a separate panel (like NeuroSync's task graph), a hover-over explanation layer (like [[augmented-semantics]]), or embedded in the semantic specification?
- ✓ **Alignment checkpoint density**: The pipeline currently has 3–4 potential pre-generation checkpoints. [[alignment-cost-tradeoff]] says these should be context-dependent, not fixed. **Partially answered by** [[uncertainty-driven-elicitation]] (InterQuest): checkpoint surfacing should be driven by knowledge entropy — surface the checkpoint where the system's uncertainty is highest, suppress where it's confident. This makes the decision dynamic and principled rather than heuristic or user-selected. Remaining gap: implementing entropy computation across the pipeline's heterogeneous knowledge stores (pattern confidence is different from user model confidence is different from intent decomposition confidence).

Verification and oversight (from Grunde-McLaughlin et al.):
- ✓ **Temporal transparency design**: [[process-induced-overreliance]] and [[outcome-oriented-verification]] together establish a design principle: process transparency is appropriate *before* generation (for steering) but counterproductive *after* generation (for verification). The architecture sketch now reflects this split: pre-generation stages are labelled as process-oriented (user steers), post-generation stages as outcome-oriented (user verifies via Requirements/Assumptions decomposition). Remaining gap: how to handle the *transition* — does the system signal "generation complete, switching to verification mode"? And for iterative refinement cycles, does each refinement reset to process mode or stay in outcome mode?
- **False confidence mitigation**: Study 3's false confidence finding (g: 0.85) means better verification tools alone don't improve outcomes — they can make users *more wrong and more confident*. The pipeline's post-generation verification needs mechanisms that break through the confidence ceiling. Candidates: requiring users to evaluate each assumption against their domain knowledge ([[cognitive-engagement-for-reliance]]), showing what the system *didn't* include (negative space surfacing), or flagging low-confidence assumptions for explicit review ([[uncertainty-driven-elicitation]]).
- **Requirements/Assumptions decomposition**: [[outcome-oriented-verification]]'s decomposition maps directly to the pipeline: Requirements = explicit intent from the user prompt (traceable via [[intent-output-traceability]]); Assumptions = inferred intent from the LLM's domain knowledge and pattern selections. The pipeline should be able to classify each generated component as requirement-driven or assumption-driven. Open question: how reliable is this classification? And should it be surfaced always or only when the system detects the user is in a verification phase?

Meta:
- End-user **mental models** of the underlying pattern structure, not just data. Park et al.'s semantic framework addresses this partially — users understand Product/Design System/Feature/Component more readily than Task/Dialog/Presentation/Layout.
- **Inspectability** of pattern composition hierarchies — users need to understand *why* a task mapped to this UI. [[augmented-semantics]] are a first step — they show what the AI did, mapped to the user's vocabulary. [[parallel-state-display]] extends this from post-hoc extraction to continuous monitoring.
- Reliability of LLM-generated specifications — how do we evaluate "good" vs "bad" pattern selections?
